# Изолированное окружение django test

## Подготовка и запуск

Предпосылки: зависимости из `pyproject.toml`, Python 3.13 и PostgreSQL **18.6**
(`initdb`, `pg_ctl` в PATH). Версия сверена с рабочим локальным PostgreSQL
06.10.2026. Используется отдельный нативный кластер, поэтому Docker daemon
не требуется. Скрипт не обращается к основной БД и не меняет её роль.

```sh
.venv/bin/python scripts/test_postgres.py start
.venv/bin/python manage.py test tests --settings=fishsite.settings_test --noinput
```

`start` создаёт `.env.test` со случайным паролем и правами 0600, если файла
ещё нет. При ручной настройке скопируйте `.env.test.example` и замените пароль.
Все пять `FISHSITE_TEST_DB_*` обязательны. Переменные процесса имеют приоритет
над `.env.test`. Пароль не выводится и не передаётся аргументом командной строки.
Кластер и сокет находятся в игнорируемом `.test-postgres/`; каталог имеет права
0700. Локальный административный сокет предназначен только для управления
этим кластером; тестовый профиль использует TCP и роль `fishsite_tester`.

```sh
.venv/bin/python scripts/test_postgres.py status
.venv/bin/python scripts/test_postgres.py stop
```

Остановка сохраняет файлы кластера. При занятом порте проверяйте
`.test-postgres/postgres.log`; не переключайте профиль на порт основной БД.
Запуск требует разрешённых локальных сокетов/shared memory. Ограниченный
sandbox может блокировать их даже при исправной конфигурации.

## Изоляция

- Единственный адрес: `127.0.0.1:15432`, cluster_name `fishsite-tests`.
- Роль: `fishsite_tester`, `LOGIN CREATEDB NOSUPERUSER NOCREATEROLE NOREPLICATION`.
- `.env.test` задаёт `NAME=postgres` только для служебного подключения runner.
  `TEST.NAME` жёстко задан как `test_fishsite`. PostgreSQL HBA разрешает роли
  только эти два имени; остальные подключения отклоняются.
- `manage.py test` выбирает `fishsite.settings_test` автоматически, даже при
  унаследованном обычном `DJANGO_SETTINGS_MODULE`. Явный другой профиль
  отклоняется. Обычные настройки также назначают runner, отказывающийся
  запускать тесты без тестового профиля (например, через `django-admin`).
- `.env` не загружается, обычные переменные приложения/SMTP не используются.
  Почта по умолчанию — locmem и синтетический no-op адаптер. В SMTP-тестах
  явные override направляют транспорт в loopback-сервер или моки. Audit hook
  запрещает соединения Python socket с внешними адресами, включая Mail.ru.
- Backend проверяет конфигурацию до подключения и фактическую БД, роль,
  порт, cluster_name и права роли после подключения. Перед SQL `flush` и
  удалением тестовой БД фактическое подключение проверяется повторно.
- Worker subprocess получает allowlist окружения с активным именем тестовой
  БД и синтетическим адаптером. Штатные SMTP-проверки парсинга настроек,
  использующие обычный профиль в subprocess, явно отключают загрузку `.env`.
- Старый `run_primary_request_scenarios.py` всегда возвращает код 2 до импорта
  Django, включая `--apply-migrations`. Тестирование основной БД запрещено.

Это защита от ошибочной конфигурации и случайных побочных действий; она не
является песочницей для произвольного недоверенного кода. Обычный рабочий
профиль и отдельная ручная отправка Mail.ru продолжают использовать свои настройки.

## Жизненный цикл и воспроизводимость

Django создаёт `test_fishsite`, применяет весь граф миграций, запускает тесты
и удаляет БД. `TestCase` откатывает свои транзакции; `TransactionTestCase`
очищает таблицы и позволяет проверять настоящий commit/rollback и несколько
подключений. Все данные создаются тестами; копирование основной БД не требуется.

Для проверки воспроизводимости выполните полную команду дважды. В обоих
прогонах должны быть сообщения `Creating test database`, `OK`,
`Destroying test database`. С `--verbosity=2` видны применённые миграции.
Тест subprocess проверяет SIGTERM, SIGKILL, восстановление lease и ожидание
завершения процесса, в том числе cleanup при ошибке.

```sh
.venv/bin/python manage.py test tests --settings=fishsite.settings_test --noinput --keepdb
```

`--keepdb` сохраняет БД, но не гарантирует сохранение данных. Следующий запуск
без этого флага с `--noinput` пересоздаст оставшуюся БД. Прогоны должны идти
последовательно: `--parallel` и параллельные запуски в разных терминалах
не поддерживаются, поскольку разрешено одно фиксированное имя БД.

Проверки без БД можно запускать без работающего PostgreSQL, но с заполненным
тестовым окружением:

```sh
.venv/bin/python manage.py test tests.test_test_environment.TestEnvironmentGuards --noinput
```

Документация Django: [тестовая БД](https://docs.djangoproject.com/en/5.2/topics/testing/overview/#the-test-database),
[TransactionTestCase](https://docs.djangoproject.com/en/5.2/topics/testing/tools/#transactiontestcase).
