# Изолированное окружение Django test

Тесты используют отдельный локальный PostgreSQL-кластер и не подключаются к основной БД или
внешним сервисам.

## Подготовка и запуск

Нужен PostgreSQL 18.6 с initdb и pg_ctl в PATH. Версия нужна для выделенного локального кластера
и проверяется скриптом.

~~~sh
.venv/bin/python scripts/test_postgres.py start
.venv/bin/python manage.py test tests --settings=fishsite.settings_test --noinput
.venv/bin/python scripts/test_postgres.py status
.venv/bin/python scripts/test_postgres.py stop
~~~

Шаблон .env.test.example задаёт окружение. При первом start скрипт создаёт .env.test со
случайным паролем и правами 0600, если файла ещё нет. Не печатай пароль и не добавляй файл в
Git. Кластер и его журналы находятся в игнорируемом .test-postgres/; остановка сохраняет его для
следующего запуска.

## Защитные границы

В GitHub Actions тот же профиль запускается с Docker `postgres:18.6`, loopback networking,
портом 15432 и HBA из `deploy/ci/`. Идентичность сервера и ограничения остаются теми же;
пароли синтетические, production secrets job не получает. Подробности — [CI/CD](ci-cd.md).

- scripts/test_postgres.py работает только со своим .test-postgres/, сверяет версии бинарных
  файлов и идентичность отдельного кластера до настройки. Только после этой проверки он создаёт
  или меняет тестовую роль.
- settings_test читает .env.test и FISHSITE_TEST_DB_*; обычный .env, SMTP credentials и
  настройки основной БД не загружаются.
- Backend разрешает служебную БД postgres и только тестовую test_fishsite; тестовый профиль
  проверяет параметры и фактическую идентичность PostgreSQL перед соединением, очисткой и
  удалением БД.
- Django runner создаёт и удаляет test_fishsite. Почта заменена на locmem, backend уведомлений —
  на синтетический; тестовый процесс запрещает сетевые подключения вне loopback.
- Worker subprocess получает ограниченный allowlist окружения. Реальная SMTP/МойСклад-интеграция
  в тестовом профиле недоступна.

Запуски выполняй последовательно. --parallel и параллельные прогоны не поддерживаются
фиксированным именем тестовой БД. --keepdb сохраняет базу между прогонами, поэтому используй его
только когда это нужно.

Для реальной проверки Mail.ru используй отдельную процедуру с синтетическими данными — тестовый
профиль намеренно блокирует внешние подключения. Текущее покрытие видно в tests/; результаты
отдельных запусков не являются постоянной характеристикой следующего прогона.
