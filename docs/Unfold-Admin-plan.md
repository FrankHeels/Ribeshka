# FishSite: план реализации Django Unfold Admin Panel

Дата исследования: **10 октября 2026 года**. Статус: **план реализации, административная панель Unfold ещё не реализована**.

План основан на исследовании рабочей копии FishSite и официальной документации от указанной даты. Он описывает кабинет владельца: интерфейс, редакционные модели, роли, вход, действия и приёмку.

Связанный документ: [план интеграции МойСклад](MoySklad-plan.md). Внешние связи, API, синхронизация прайса, модель и правила временной цены, экспорт заявок, очередь и вебхуки реализуются по этому документу. Кабинет использует их сервисы и сохранённые результаты.

## 1. Целевой результат и границы

Владелец оформляет ассортимент и содержание сайта через простой кабинет в стиле FishSite. Он видит новые заявки и состояние обмена, может исправить оформление товара и выполнить разрешённое действие без доступа к техническим настройкам.

| Область | Решение |
|---|---|
| Товары | Публичное название, тексты, галерея, категория, публикация, порядок, популярность, SEO |
| Рекомендации | Явный выбор двух товаров для главной и их порядка |
| Заявки | Контакты и неизменяемые позиции, служебные заметки/ответственный, состояние передачи и учётный статус |
| Контент | Фиксированные страницы, баннер/обложка, контакты, график и условия доставки |
| МойСклад | Сопоставление товаров, read-only прайс, диагностика, фоновые действия; без токенов и инфраструктурных настроек |
| Цена | Отдельная форма временного исключения с причиной, автором и сроком; расчёт выполняет общий сервис цены |
| Доступ | Владелец без superuser, отдельные права на действия, HTTPS, ограничение попыток входа и 2FA |
| Остатки | Не отображаются и не управляются; наличие подтверждает менеджер |

Розничные и оптовые цены ведутся в МойСклад. Публичный сайт использует розничную цену; оптовая форма остаётся контактной, без корзины и прайса. Оплата, резервы и отгрузки в кабинете сайта не добавляются.

Кабинет сохраняет Django Admin и серверные шаблоны внутри существующего модульного монолита. Отдельное клиентское приложение и публичный REST API не требуются. Первый совместный релиз включает передачу розничных заявок в МойСклад по связанному плану.

## 2. Исходное состояние и необходимые дополнения

Исходная точка проверена при исследовании 10 октября 2026 года, включая незакоммиченные изменения рабочей копии. Перед реализацией повторно проверить затрагиваемые пути.

| Уже есть | Где | Как использовать |
|---|---|---|
| Django 5.2.17, Python 3.13, стандартный admin | `pyproject.toml`, `fishsite/settings.py` | Добавить Unfold без обновления Django ради темы |
| Товар, плоская категория, цена/кг, публикация, галерея | `catalog/models.py`, `catalog/admin.py` | Сохранить ID, slug, фото, formset-проверку одного основного изображения |
| Неизменяемые позиции и read-only заявки | `orders/models.py`, `orders/admin.py`, `inquiries/admin.py` | Дополнить служебной обработкой, не разрешая менять историю |
| Фиксированные страницы, текстовые блоки и SEO страниц | `content/models.py`, `content/admin.py` | Удобные формы поверх существующих моделей |
| Архив редакций согласия | `content/consent_revisions.py`, модели заявок | Read-only история; юридические тексты остаются в Markdown |
| Почтовая очередь и административный повтор | `integrations/notifications/`, `integrations/admin.py` | Сохранить действующий сценарий и независимость от МойСклад |

Пока нет Unfold, роли владельца и обязательной 2FA. Не хватает ручного порядка товаров, популярности, собственного SEO товаров/категорий, структурированных контактов/графика и баннера. Главная сейчас выбирает первые два опубликованных товара по названию.

Нет интерфейсов внешней связи, свежести прайса, временной цены и результата экспорта. Данные и сервисы для них добавляются по [плану МойСклад](MoySklad-plan.md), а интерфейсы — по этому плану.

## 3. Владение данными и контракт с интеграцией

| Данные | Главный источник | Поведение второго приложения |
|---|---|---|
| UUID, артикул, учётное название, единица учёта | МойСклад | Django хранит служебную копию и показывает её для справки |
| Розничный прайс | МойСклад | Django хранит последнюю корректную цену и время её проверки |
| Оптовый прайс | МойСклад | В первом релизе сайт его не использует |
| Название на сайте, slug, тексты, фотографии | Django | Синхронизация их не перезаписывает |
| Категория сайта, порядок, публикация, популярность, рекомендации | Django | Классификация склада не меняет навигацию магазина |
| Временная цена сайта | Django, исключение с ограниченным сроком | В МойСклад прайс не меняется; заказ передаётся по цене принятой заявки |
| Исходная заявка и её снимки | Django | В МойСклад создаётся учётный документ на её основе |
| Статус продажи, согласованный состав, фактический вес и итог после передачи | МойСклад | Django показывает статус и при необходимости отдельный согласованный итог; исходную заявку не переписывает |
| Факт просмотра заявки, ответственный, внутренняя заметка | Django | Это служебная работа кабинета, не второй статус продажи |
| Состояние экспорта и повторы | Django | Не смешивается со статусами «подтверждён», «отгружен» и т. п. |

Один товар МойСклад соответствует одной карточке сайта. Изменение учётного названия не меняет публичное название и URL. «Восстановить название из МойСклад» допустимо отдельным осознанным действием.

### Граница реализации

| Возможность | Реализуется в этом плане | Предоставляет план МойСклад |
|---|---|---|
| Связь товара | Экран кандидатов/сопоставления, оформление и подтверждение | Реестр `MoySkladProduct`, проверки UUID/единицы/цены, сервис изменения связи |
| Временная цена | Форма, причина/срок, отображение источника, право `override_price` | `PriceOverride`, `effective_price`, журнал и правила окончания |
| Обновить цены / повторить передачу | Защищённые действия, сообщения о ходе и результате | Сохранение задачи, дедупликация, retry, неизменный `syncId` |
| Заявки | Карточки, фильтры, служебные заметки/ответственный | Снимки, `MoySkladOrderLink`, состояние передачи и учётный статус |
| Мониторинг | Дашборд, списки ошибок, время проверки и охват | Локальные результаты сверки, очередь, heartbeat, безопасные коды ошибок |

Дашборд и формы не вызывают API МойСклад при рендеринге. Фоновые действия возвращают подтверждение постановки и затем показывают результат из БД. Права проверяются сервером, а не только видимостью кнопки.

Базовое оформление и контент можно реализовать до готовности интеграции. Внешние данные в этом режиме обозначаются «Не подключено», зависимые действия недоступны с объяснением. До подключения источника существующая локальная цена остаётся в действующем режиме; для связанного товара прайс становится read-only. Временная цена активируется только вместе с общим сервисом расчёта, чтобы витрина и заявка не расходились.

На дату исследования в PyPI опубликован `django-unfold 0.108.0`; заявлены Python 3.13 и Django 5.2. Перед установкой зафиксировать выбранную совместимую версию в `pyproject.toml` и lock-файле, затем проверить существующие admin-формы. Совместимость заявлена пакетом, но интеграция с FishSite ещё не запускалась. [Релиз и требования](https://pypi.org/project/django-unfold/).

### Навигация

| Раздел | Содержимое |
|---|---|
| Обзор | Новые заявки, проблемы передачи, товары без оформления, состояние прайса, быстрые действия |
| Товары | Карточки сайта, новые позиции из МойСклад, категории |
| Заявки | Розничные и оптовые, раздельные вкладки |
| Содержание сайта | Главная, рекомендации, страницы, контакты и график, SEO |
| МойСклад | Состояние обмена, связанные товары, ошибки и история запусков |

Группы Django, сессии, сырые очереди, ключи, технические ID и настройки инфраструктуры не нужны в ежедневном меню владельца. Их доступность ограничивается правами на сервере, а не только скрытием ссылок.

### Главный экран

Первый экран отвечает на три вопроса: появились ли заявки, какие товары надо оформить, работает ли обмен.

Показывать счётчики со ссылками: «Новые розничные», «Новые оптовые», «Нужна помощь с передачей», «Товары без фото», «Активные временные цены». Ниже — последние заявки и проблемы, требующие действия. Статус прайса содержит время проверки и охват, например «Проверено 38 из 40 товаров; 2 требуют настройки».

Основные кнопки: «Открыть новые заявки», «Добавить из МойСклад», «Проверить цены». Последняя запускает фоновую задачу и показывает её результат; она не удерживает HTTP-запрос до конца импорта.

### Список и карточка товара

Список: миниатюра, название сайта, артикул, категория, цена сайта, источник цены, публикация, результат синхронизации. Поиск по публичному и учётному названию, артикулу. Фильтры: опубликован/скрыт, категория, нет фото, не связан, ошибка цены, временная цена, популярный.

Карточка имеет понятные вкладки:

| Вкладка | Действия |
|---|---|
| На сайте | Название, категория, краткое/полное описание, публикация, порядок, популярность |
| Фотографии | Загрузка нескольких файлов, миниатюры, основное фото, alt-текст, порядок |
| Цена | Цена сайта, прайс МойСклад, время проверки, причина/срок временной цены, история |
| Поиск и SEO | Заголовок, описание, preview поискового сниппета, slug с предупреждением об изменении URL |
| МойСклад | Учётное название, артикул, единица, состояние связи, кнопка открытия исходной позиции |

Основные действия — «Сохранить», «Посмотреть на сайте», «Скрыть/Опубликовать». Для черновика — защищённый предварительный просмотр только сотруднику; нельзя делать скрытый товар общедоступным ради preview.

Сохраняются действующие ограничения на одно основное фото. Проверять формат, размер и разрешение загружаемых изображений, давать понятные ошибки. Сортировка перетаскиванием имеет альтернативу кнопками/полем порядка. Скрытый товар не появляется в поиске, рекомендациях, меню и прямом публичном URL.

### Рекомендации и популярные товары

На главной сохраняются два места под рекомендации, но владелец выбирает товары и их порядок явно. В выборке — только доступные для публикации товары. Если выбранный товар скрыт, слот перестаёт его показывать; кабинет объясняет причину, случайной замены нет. При миграции можно сохранить текущие два товара как первоначальный выбор.

Признак «Популярный» — ручная редакционная отметка, не вычисленная статистика продаж. Её использовать для согласованного бейджа/фильтра каталога; автоматическую аналитику покупок не добавлять.

### Заявки

В списке розничных заявок: номер, дата, имя, телефон, предварительная сумма, получение, передача в МойСклад, учётный статус. Фильтры «Новые», «Не переданы», «Нужна помощь». В карточке — сохранённые позиции, контакты, комментарий, доставка, история событий и ссылка «Открыть в МойСклад».

Снимки и факт согласия доступны для чтения. Редактируются только служебные заметки/ответственный. Причины ошибки формулируются по делу: «Не выбран розничный прайс», «Товар не связан», «Нет доступа к МойСклад». HTTP-коды и ID доступны специалисту в подробностях.

Оптовые заявки имеют локальные состояния «Новая», «Связались», «Закрыта» и заметки: их форма не содержит товарного состава для автоматического экспорта.

### Контент и оформление

Существующие `ContentPage`/`ContentSection` остаются основой. Вместо технических ключей показывать формы «Обложка», «О компании», «Условия доставки», «Контакты». Контакты и график хранить в структурированных общих настройках и использовать повторно на нужных страницах.

Для баннера добавить ограниченный набор полей: изображение, alt-текст, заголовок, текст, разрешённая ссылка и публикация. Начать с одной обложки; произвольный конструктор страниц и слайдер не требуются. Пустое изображение сохраняет текущий макет.

Юридические тексты сейчас принадлежат Markdown-файлам и архиву редакций. Их не превращать незаметно в обычные редактируемые блоки: кабинет показывает ссылку и пояснение о процессе обновления.

Кабинет использует логотип, тёплые нейтральные поверхности, латунный акцент и локальный Golos Text. Рабочие таблицы — на спокойном однотонном фоне; светлая тема по умолчанию, тёмная по выбору. Цвет статуса сопровождается текстом. Сохранение сообщает результат, ошибки стоят рядом с полем, фокус видим. Проверить 375/768/1280/1440 px, клавиатуру и увеличение масштаба.

### Техническая настройка Unfold

- Добавить `unfold` перед `django.contrib.admin`; перевести используемые `ModelAdmin` и inlines на классы Unfold, сохранив собственные проверки и запреты. [Установка](https://unfoldadmin.com/docs/installation/quickstart/).
- Дашборд: `templates/admin/index.html`, `DASHBOARD_CALLBACK`, запросы с учётом прав и без вызовов внешнего API. [Дашборд](https://unfoldadmin.com/docs/configuration/dashboard/).
- Сопоставление товаров и монитор интеграции: специализированные страницы с `UnfoldModelAdminViewMixin`, явными разрешениями и `admin_site.admin_view`. Их URL регистрировать с проверкой конфликтов стандартного admin. [Пользовательские страницы](https://unfoldadmin.com/docs/configuration/custom-pages/).
- Дополнительный CSS кабинета отделить от публичного `site.css`. Пользовательские классы Tailwind требуют собственной сборки; стандартные компоненты и небольшой отдельный CSS позволят начать без второй сложной сборочной цепочки.
- Unfold предоставляет интерфейсные средства; сопоставление, очередь, редакционная модель и защита от дублей реализуются в FishSite.

## 5. Временная цена и действия с МойСклад

### Временная цена

Это отдельная функция, а не разблокировка обычного поля прайса:

- Действие «Установить временную цену»: сумма, обязательная причина, срок и автор. Предлагаемый срок по умолчанию — 24 часа, настраиваемый и требующий подтверждения владельца.
- На карточке одновременно видны цена сайта, последняя цена МойСклад, источник и момент окончания исключения.
- Синхронизация продолжает обновлять базовый прайс, не уничтожая активное исключение.
- После срока действует актуальная сохранённая базовая цена; при её устаревании кабинет показывает предупреждение. Уведомление об окончании не должно быть единственным механизмом возврата.
- Расчёт эффективной цены проверяет срок при каждом чтении. Остановившийся worker не продлевает временную цену.
- Возврат к прайсу, установка и замена исключения журналируются. Право на эту операцию отделено от редактирования описаний.

Нужен единый серверный механизм `effective_price(product, at)`, возвращающий сумму и источник. Через него должны проходить карточки, рекомендации, корзина, подписанный снимок, повторная проверка POST и создание `OrderItem`. Нельзя оставить часть кода читающей базовое поле напрямую. Один момент `at` используется на весь расчёт; блокировка `Product` сериализует изменение базовой/временной цены и принятие заказа.

Экспорт передаёт цену из `OrderItem.price_per_kg_snapshot`, включая временную. После возврата к прайсу уже принятая заявка не дорожает и не дешевеет.

Этот раздел фиксирует контракт формы. Модель `PriceOverride`, сервис `effective_price`, транзакционные проверки и обновление читателей цены реализуются по [плану МойСклад](MoySklad-plan.md), без второй реализации в admin.

### Сопоставление и восстановление

Показать существующую карточку, кандидата МойСклад, артикул, учётное название, единицу и цену. Не предлагать автоматическое подтверждение неоднозначного совпадения. Новая позиция сначала оформляется и остаётся неопубликованной.

«Повторить передачу» возобновляет ту же задачу. «Связать с существующим заказом» доступно при ручном разборе после проверки номера, состава и отсутствия занятой связи. При неизвестном результате предыдущей попытки сначала выясняется наличие документа по прежнему `syncId`; UI не создаёт новый документ или ключ самостоятельно.

Перепривязка товара и временная цена требуют причины/подтверждения и журнала. Старые снимки не переписываются. Неисправная внешняя связь, архивный товар или недопустимая единица показываются как разные проблемы; остатки не участвуют в решениях.

### Состояния обмена

Различать время проверки доступа, успешной сверки каталога, конкретной цены, экспорта и heartbeat worker. Показывать возраст старейшей ожидающей заявки, число ошибок и активные временные цены. Один успешный товар не означает актуальность всего каталога.

Полные контакты доступны только в защищённой карточке заявки. На дашборде и в диагностике не выводятся токены, тела API-запросов и необработанные исключения.

## 6. Модели и размещение кода

Имена ниже — предлагаемый контракт, а не готовые миграции.

| Модель / изменение | Назначение и ограничения |
|---|---|
| `Product`: редакционные поля | `display_order`, `is_popular`, SEO. Существующие публичное название, slug, категория, описания, публикация и галерея сохраняются |
| `Category` | SEO-поля с текущим fallback, сохранение плоской структуры |
| `Order` / `Inquiry` | Отдельные поля служебной обработки и внутренние заметки; оптовые локальные статусы не создают учётный заказ |
| `HomepageRecommendation` в `content` | Два явных слота главной, ссылки на товары, уникальность слота и товара |
| `SiteSettings` / `HomepageSettings` | Единственные записи общих контактов/графика и оформления обложки; валидированные поля, без секретов и произвольного HTML |

Действия сотрудников записываются в существующий Admin LogEntry. Сохраняются ограничения удаления заявок и архива согласий, неизменяемость `OrderItem`, фиксированные ключи страниц и одно основное фото.

Внешний реестр `MoySkladProduct`, `MoySkladOrderLink`, `MoySkladTask`, `MoySkladWebhookInbox`, `MoySkladSyncState`/`MoySkladSyncRun`, `PriceOverride`, интеграционная блокировка `Product` и внешние снимки `OrderItem` добавляются по [плану МойСклад](MoySklad-plan.md). Админка использует их, а не создаёт дублирующие модели. Миграции общих приложений `catalog`, `orders` и `content` согласовать между направлениями.

```text
fishsite/backoffice/   # конфигурация Unfold, навигация, дашборд, доступ
catalog/admin.py       # товары, категории, фото и формы цены
orders/admin.py        # розничные заявки и их служебная обработка
inquiries/admin.py     # оптовые заявки и локальные статусы
content/admin.py       # страницы, контакты, обложка, рекомендации
integrations/admin.py  # отображение обмена и действия через сервисы
templates/admin/      # специализированные экраны кабинета
static/admin/          # изолированные стили кабинета
```

Модели и миграции остаются в соответствующих существующих Django-приложениях. `content` владеет содержанием страниц, `catalog` — каталогом, `orders`/`inquiries` — заявками. `fishsite/backoffice/` объединяет оформление и навигацию, не забирая в себя доменную логику.

## 7. Права, вход и журнал действий

| Роль | Разрешения |
|---|---|
| Владелец | Товары и контент, заявки, рекомендации, временная цена, безопасный повтор/запрос синхронизации |
| Контент-редактор, если нужен | Фото, описания, категории и страницы; без контактов заявок и изменения цены |
| Технический администратор | Связи, конфигурация, разбор конфликтов, обслуживание пользователей и журналов |

Владелец — обычный `is_staff` с группой разрешений, без `is_superuser`. Отдельные права: `override_price`, `retry_moysklad_export`, `run_catalog_sync`, `manage_moysklad_mapping`. Проверять их в POST-обработчиках и сервисных действиях; скрытая кнопка не является защитой.

Все изменения — POST с CSRF. Массовое скрытие, перепривязка и временная цена показывают краткое подтверждение последствий. Обычное сохранение текста не требует лишнего диалога. Удаление заявок, снимков и архива согласий остаётся закрытым.

Для публичного запуска: HTTPS, secure cookies, корректные proxy-заголовки, ограничения попыток входа по учётной записи и IP, обязательная 2FA для персонала с контактами покупателей. Кандидат для TOTP — `django-two-factor-auth`; на этапе подключения проверить выбранную версию и совместный AdminSite с Unfold. Защита должна проверять подтверждённую OTP-сессию на всех admin-страницах: одной замены формы входа недостаточно. Нужны резервные коды и документированное восстановление доступа. [Требования к защите AdminSite](https://django-two-factor-auth.readthedocs.io/en/stable/implementing.html).

Токен МойСклад не показывается в формах и не передаётся браузеру. Права API-пользователя и защита webhook определены в [плане МойСклад](MoySklad-plan.md); оператор кабинета работает через ограниченные сервисные действия.

Юридические тексты сейчас принадлежат Markdown-файлам и архиву редакций. В кабинете сохраняется read-only доступ; перед вводом обмена процесс передачи контактов и сроки хранения обновляются в соответствующих документах совместно с интеграцией.

## 8. Порядок реализации и условия завершения

| Этап | Работа | Результат / критерий перехода |
|---|---|---|
| 0. Подготовка | Проверить текущие admin-классы, требования владельца, совместимость Unfold и выбранной 2FA; согласовать контракт действий интеграции | Зафиксированы версия, роли и границы двух планов |
| 1. Основа Unfold | Зависимость и lock-файл, настройки, ModelAdmin/inlines, навигация, изолированные стили | Все существующие формы работают, проверки и запреты сохранены |
| 2. Редакционные модели | Порядок/популярность/SEO, рекомендации, контакты/график/обложка, служебные поля заявок | Добавочные миграции сохраняют текущий контент, URL, фотографии и заявки |
| 3. Товары и контент | Формы, галерея, поиск/фильтры, публикация, preview, два слота рекомендаций, страницы | Владелец оформляет и публикует товар без технических полей |
| 4. Заявки и обзор | Список и карточки, служебные заметки/ответственный, локальные статусы опта, дашборд | Исходная заявка неизменяема, новые обращения видны, сумма заявок не называется выручкой |
| 5. Экраны интеграции | Сопоставление, read-only прайс, временная цена, монитор, фоновые действия, ссылка на учётный заказ | Интерфейс использует готовые сервисы из плана МойСклад; ошибки и повторы понятны владельцу |
| 6. Доступ и безопасность | Группы и права, серверные проверки POST, CSRF, HTTPS, ограничение входа, обязательная 2FA и восстановление | Доступ закрыт без прав и подтверждённой OTP-сессии, включая прямые URL |
| 7. Приёмка и ввод | Проверки сценариев, адаптивности и регрессий; демонстрация владельцу; обновление документов | Повседневная работа выполняется без superuser, готова диагностика до живого экспорта |

Экраны интеграции можно готовить на тестовых данных, пока её сервисы разрабатываются. В рабочем окружении соответствующие действия включаются после проверки настоящих сервисов. Разделение планов не отменяет совместную приёмку цепочки «изменение цены → заявка → заказ в МойСклад».

## 9. Проверки и приёмка

| Область | Обязательные сценарии |
|---|---|
| Права | Владелец без superuser; контент-редактор без заявок/цены; прямые URL и POST без прав; скрытие меню не заменяет авторизацию |
| Вход | OTP не подтверждён; все admin-страницы и альтернативные входы; ограничение попыток; резервные коды и восстановление |
| Товар и галерея | Поиск по обоим названиям/артикулу; фильтры; загрузка и ограничения файлов; смена основного фото; порядок без мыши |
| Публикация | Скрытие во всех списках, рекомендациях, меню, поиске и прямом URL; защищённый preview черновика |
| Рекомендации | Два явных слота, отсутствие дублей, порядок, скрытый товар не заменяется случайным |
| Контент и SEO | Фиксированные страницы; контакты/график в нужных местах; пустой баннер; SEO fallback; Markdown юридических текстов не подменён CMS-блоками |
| Заявки | Контакты по правам, неизменяемые снимки/согласия, служебные поля отдельно от учётного статуса, локальные статусы опта |
| Временная цена | Право, причина, срок, отмена, источник и история; обновление базового прайса во время исключения; истечение при остановленном worker |
| Интеграция | Не подключена, ожидание, частичная сверка, устаревший прайс, ошибка доступа, повтор передачи, ручная связь с документом |
| Отсутствие побочных эффектов | GET/рендеринг не вызывает внешний API; двойное нажатие фонового действия не создаёт дубль задачи или заказа |
| Интерфейс | 375/768/1280/1440 px, клавиатура, масштаб, видимый фокус, подписи и ошибки, статус не только цветом |
| Регрессии | Шаг 1 кг, сессионная корзина, цены и снимки, согласия, оптовая форма, независимая email-очередь, страницы сайта |

Автоматические тесты используют существующую изолированную PostgreSQL на 15432 с `fishsite.settings_test`, mock/local fake API и тестовую почту. Не использовать реальные токены и production-БД. Транзакционные проверки выполняются через `TransactionTestCase`; сценарии API/retry/webhook/восстановления полностью описаны в [плане МойСклад](MoySklad-plan.md).

### Демонстрация владельцу

1. Войти с 2FA под обычной ролью и увидеть новые обращения и состояние обмена.
2. Найти товар, изменить название/описание, загрузить фото, выбрать основное и проверить карточку сайта.
3. Оформить новую позицию из МойСклад, назначить категорию и опубликовать без повторного ввода прайса.
4. Выбрать два рекомендуемых товара и порядок; скрыть один и проверить отсутствие его во всех публичных местах.
5. Изменить контакты, график, обложку и SEO; убедиться, что юридический архив остаётся неизменяемым.
6. Открыть заявку, сохранить служебную заметку, перейти к учётному заказу, увидеть статус передачи отдельно от статуса продажи.
7. При тестовом сбое API понять причину, выполнить разрешённый повтор и убедиться, что нового документа не появилось.
8. Установить временную цену и проверить автоматический возврат к прайсу по сроку.
9. Пройти совместные сценарии из [плана МойСклад](MoySklad-plan.md): изменение прайса сохраняет оформление, заявка экспортируется со снимками, остатки не влияют на заказ.

## 10. Включение и откат

Перед вводом сохранить backup БД и media, применить добавочные миграции и проверить существующие карточки/URL/заявки. При переносе рекомендаций сохранить текущие два товара как первоначальный выбор, если они подходят для публикации.

Последовательность: Unfold и изолированные стили → роли и защищённый вход → товары/контент → заявки/обзор → подключение готовых сервисов МойСклад → совместная демонстрация → выдача доступа владельцу. Защита должна быть готова до предоставления рабочего доступа с контактами покупателей.

Живой экспорт включается по [плану МойСклад](MoySklad-plan.md) после готовности его диагностики и ручного восстановления в кабинете. Подключение Unfold само по себе не ставит старые заявки на экспорт и не меняет цену или внешний прайс.

При откате интерфейса сохранять новые данные, связи, временные цены и очередь. Не откатывать схему с потерей контента. Предыдущая версия admin допустима только при сохранении тех же прав, 2FA и запрета редактирования снимков/синхронизируемых полей. Если это не обеспечивается, закрыть административный доступ на время исправления, сохранив работу сайта и фоновых сервисов. Остановка/откат интеграции выполняется отдельно по её плану.

## 11. Что определить до внедрения

- Кто пользуется кабинетом и нужны ли отдельные роли контент-редактора и технического администратора.
- Кто вправе устанавливать временную цену, менять связь с учётным товаром и повторять экспорт; срок исключения и порядок разбора ошибок согласуются с планом интеграции.
- Какие контакты, график и материалы обложки предоставит владелец; какой набор товаров используется для демонстрации.
- Удобство предложенных разделов и карточки товара, основной рабочий размер экрана.
- Выбранная совместимая конфигурация Unfold и 2FA, способ выдачи резервных кодов и восстановления доступа.
- Готовность моделей и сервисов МойСклад для включения зависимых действий.

Тариф, API-права, типы цен, единицы, организация, контрагент и налоговые настройки уточняются в [плане МойСклад](MoySklad-plan.md). Остатки, оптовый прайс на сайте, клиентский кабинет, онлайн-оплата, произвольный конструктор страниц и расширенная аналитика не входят в этот объём.
