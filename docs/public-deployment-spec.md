# Спецификация публичного деплоя FishSite

Дата: 9 октября 2026 года. Тип: спецификация процесса и необходимой инфраструктуры.
Статус: подготовлена к согласованию границы приёмки; инфраструктурные изменения и публичный деплой этой спецификацией не выполнены.

## Problem Statement

Владельцу FishSite нужно открыть сайт по собственному домену и принимать розничные и оптовые заявки. Посетитель должен видеть действующий ассортимент и фотографии, сотрудник — сохранённые заявки в админке и почтовые уведомления. После перезапуска сервера, обновления приложения или потери VPS данные должны сохраняться либо восстанавливаться по описанной процедуре.

Исходный план правильно определяет стек, но недостаточно описывает первый выпуск сертификата, доверие к прокси, фактическую доступность Docker-портов, воспроизводимость релиза, права приложения в PostgreSQL, перенос контента, согласованность копий базы и фотографий, работу восстановленной очереди и откат после миграций. Простого запуска контейнеров недостаточно для подтверждения готовности сайта.

Проверка текущего репозитория установила:

- Приложение — модульный Django-монолит с серверными шаблонами; используются PostgreSQL, Gunicorn, Nginx и отдельный worker уведомлений.
- Compose публикует только HTTP-порт Nginx, по умолчанию 8000. Порты PostgreSQL и Gunicorn на хост не публикуются. Сертификаты и автоматическое продление пока не настроены.
- PostgreSQL указан как 18.6, Python — 3.13, Django — 5.2.17; Python-зависимости фиксируются lock-файлом. Nginx и базовый образ приложения используют изменяемые теги.
- В текущем Compose приложение и worker получают учётные данные роли, создаваемой официальным образом PostgreSQL при инициализации. Эта роль является суперпользователем; для production необходимо разделить административную роль, владельца схемы и runtime-роль. [Правила инициализации официального образа PostgreSQL](https://github.com/docker-library/docs/blob/master/postgres/README.md).
- Nginx уже перезаписывает `X-Real-IP` и `X-Forwarded-Proto`; приложение использует доверенный IP для ограничения попыток публичных форм.
- Наличие `service_started` у web не доказывает готовность Django или наличие нужной схемы. У web нет самостоятельной проверки готовности в Compose.
- `check_notification_smtp` поддерживает только выбранный профиль Mail.ru (`smtp.mail.ru:465`, SSL/TLS); это не универсальная проверка произвольного SMTP-провайдера.
- Фото находятся в отдельном постоянном томе. Серверная корзина, заявки, outbox и ограничения форм зависят от PostgreSQL.
- Каталог, тексты фиксированных страниц, фотографии, заявки и очередь имеют отдельные предметные границы. Миграция создаёт записи фиксированных страниц, которые нужно учитывать при импорте.
- Карта доставки уже подключается через браузерный ключ Яндекса. Для публичного домена потребуются соответствующие ограничения ключа и проверка карты; отсутствие ключа имеет предусмотренный fallback.
- В рабочем дереве есть незакоммиченные изменения. Текущее содержимое компьютера не является утверждённым релизом.

## Solution

Развернуть один production-экземпляр FishSite на Ubuntu VPS по воспроизводимой процедуре. Сайт обслуживается через Nginx по HTTPS; PostgreSQL и Gunicorn доступны только внутри необходимых Docker-сетей. Первый запуск проходит в закрытом режиме, пока не проверены приложение, сертификат, SMTP, контент и восстановление из внешней копии.

Основная граница приёмки — реальный пользовательский путь через публичный HTTPS-домен: отправка заявки, её появление в админке и поступление уведомления в контрольный почтовый ящик. Дополнительные эксплуатационные проверки подтверждают восстановление данных, продление сертификата, сетевую изоляцию и повторный запуск. Используются существующие маршруты и команды приложения.

Процесс должен давать оператору четыре воспроизводимых результата: первый запуск, обновление, откат совместимого релиза и восстановление на новом VPS. Для каждого результата сохраняется запись о релизе и проверках без секретов и содержимого заявок.

## User Stories

1. As a владелец сайта, I want зарегистрировать выбранный домен на принадлежащую мне учётную запись, so that я управляю адресом сайта и его продлением.
2. As a владелец сайта, I want видеть сроки и ответственного за продление домена и VPS, so that сайт не отключается из-за неоплаченного обслуживания.
3. As a оператор, I want подставлять провайдера VPS и внешнего хранилища через параметры, so that процесс не зависит от конкретного поставщика.
4. As a оператор, I want получить сервер с поддерживаемой ОС и достаточным диском, so that приложение и копии помещаются и обновляются.
5. As a оператор, I want входить по SSH-ключу с разрешённых адресов, so that доступ к серверу ограничен.
6. As a оператор, I want сохранить проверенный аварийный доступ через консоль провайдера, so that я могу восстановить SSH после сетевой ошибки.
7. As a оператор, I want проверить опубликованные Docker-порты снаружи, so that база и Gunicorn не доступны из интернета.
8. As a посетитель, I want открывать понятный домен, so that мне не нужно знать IP сервера.
9. As a посетитель, I want автоматически переходить с HTTP на HTTPS, so that дальнейшая работа проходит по защищённому соединению.
10. As a оператор, I want однозначный основной hostname, so that формы, cookies и ссылки используют согласованный адрес.
11. As a оператор, I want выпустить первый сертификат без открытого HTTP-доступа к формам и админке, so that подготовка HTTPS не раскрывает приложение.
12. As a оператор, I want автоматическое продление сертификата и загрузку нового сертификата Nginx, so that HTTPS продолжает работать без ручного вмешательства.
13. As a оператор, I want получать сигнал о неудачном продлении, so that успеваю исправить проблему до окончания сертификата.
14. As a оператор, I want хранить секреты отдельно от Git и образа, so that релизы и диагностика не раскрывают учётные данные.
15. As a оператор, I want разделить права базы для миграций и приложения, so that обычные запросы не выполняются от суперпользователя.
16. As a оператор, I want разворачивать конкретный commit и конкретные образы, so that могу воспроизвести и сравнить релизы.
17. As a оператор, I want проверять схему и готовность приложения до открытия сайта, so that посетители не попадают на незавершённый запуск.
18. As a посетитель, I want видеть статику и фотографии, соответствующие странице, so that оформление и ассортимент отображаются правильно.
19. As a сотрудник, I want загружать фотографии в постоянное хранилище через админку, so that они сохраняются после пересоздания контейнеров.
20. As a владелец сайта, I want перенести только утверждённый каталог, тексты и изображения, so that production не содержит тестовых заявок и чужих аккаунтов.
21. As a оператор, I want повторяемый импорт с проверкой связей и количества записей, so that перенос можно безопасно проверить и повторить.
22. As a сотрудник, I want отдельную рабочую учётную запись с нужными правами, so that повседневная работа не требует общего суперпользователя.
23. As a посетитель, I want отправить розничную заявку с выбранными товарами и способом получения, so that продавец получает моё обращение.
24. As a оптовый покупатель, I want отправить отдельную оптовую заявку, so that сотрудник может обработать её независимо от розничной корзины.
25. As a посетитель, I want получить номер сохранённой заявки, so that могу ссылаться на неё при обращении к продавцу.
26. As a посетитель, I want сохранить заявку при временном сбое почты, so that сбой уведомления не теряет моё обращение.
27. As a сотрудник, I want получать уведомления на утверждённый адрес, so that оперативно замечаю новые заявки.
28. As a оператор, I want проверить TLS и аутентификацию Mail.ru до подключения worker, so that ошибки конфигурации выявляются до обработки очереди.
29. As a оператор, I want увидеть содержимое и статусы очереди перед стартом worker, so that не отправляю исторические или тестовые уведомления неожиданно.
30. As a сотрудник, I want видеть уведомления, требующие ручного разбора, so that могу повторить доставку после устранения причины.
31. As a оператор, I want корректное завершение worker при обновлении, so that уменьшается риск неопределённого результата отправки.
32. As a владелец сайта, I want внешние зашифрованные копии базы и фотографий, so that потеря VPS не означает потерю всех данных.
33. As a оператор, I want согласованную пару базы и media с идентификатором копии, so that фотографии соответствуют восстановленным записям.
34. As a оператор, I want проверить восстановление из скачанной внешней копии, so that знаю, что резервирование действительно работает.
35. As a оператор, I want запретить SMTP в среде восстановления, so that проверка копии не отправляет письма реальным получателям.
36. As a владелец сайта, I want измеряемые цели по потере данных и сроку восстановления, so that понимаю последствия аварии.
37. As a оператор, I want наблюдать доступность сайта, диск, копии и очередь, so that замечаю неисправности до жалоб посетителей.
38. As a оператор, I want безопасные журналы с ограниченным размером, so that могу разбирать ошибки без утечки данных и заполнения диска.
39. As a оператор, I want обновлять сайт в управляемом окне обслуживания, so that миграции и версии приложения не конфликтуют.
40. As a оператор, I want знать совместимость схемы перед откатом, so that возврат образа не повреждает данные и не ломает запросы.
41. As a оператор, I want сохранять новые заявки при выборе способа отката, so that восстановление старой копии не уничтожает принятые обращения незаметно.
42. As a посетитель, I want видеть понятное сообщение об обслуживании, so that понимаю, когда можно повторить обращение.
43. As a посетитель, I want пользоваться основными страницами и формами без JavaScript, so that отказ дополнительных скриптов не блокирует заявку.
44. As a посетитель, I want видеть карту доставки или предусмотренное объяснение и ссылку при её отказе, so that информация о получении товара остаётся доступной.
45. As a оператор, I want проверить запуск после перезагрузки VPS, so that сервер восстанавливает работу без интерактивных команд.
46. As a владелец сайта, I want получить протокол готовности и инструкции обслуживания, so that результат деплоя можно принять и поддерживать.

## Implementation Decisions

### 1. Границы архитектуры и результата

- Сохраняются Django Templates, PostgreSQL, Gunicorn, Nginx и outbox-worker из одного образа приложения. Redis, отдельный frontend-сервер, Kubernetes и балансировка нескольких VPS не добавляются.
- Изменяются production-конфигурация Compose, конфигурация Nginx, управление сертификатами, передача учётных данных PostgreSQL, эксплуатационные процедуры импорта, копирования, восстановления и контроля состояния.
- Бизнес-схема, публичные URL и контракт форм не меняются. Новые таблицы или публичные API для деплоя не требуются. Создание ролей PostgreSQL относится к инфраструктуре.
- Локальный HTTP-сценарий остаётся отдельным режимом. Production-конфигурация проверяется после объединения всех Compose-настроек: наличие локального порта 8000 в итоговой публикации недопустимо.
- Документы эксплуатации, Compose и индекс обновляются при реализации. Спецификация описывает целевое поведение; утверждать выполненный деплой можно только по протоколу приёмки.

### 2. Обязательные входные параметры

| Параметр | Правило |
|---|---|
| Основной домен | Уже выбран владельцем; точное имя подставляется перед исполнением. Для международного имени системные настройки используют корректное ASCII-представление. |
| Дополнительные hostnames | По умолчанию отсутствуют. `www` добавляется только явно, с DNS, сертификатом и перенаправлением на основной адрес. |
| VPS | Провайдер, регион, публичный IPv4, доступ к консоли, срок оплаты. Регион выбирается владельцем до загрузки рабочих данных. |
| Доступ оператора | SSH-ключ, разрешённые IPv4/IPv6 или VPN для SSH и административного доступа, аварийная консоль. |
| Релиз | Утверждённый Git commit, идентификатор релиза, сохранённые образы и их digests, предыдущий принятый релиз при обновлении. |
| Почта | Mail.ru-ящик отправителя, пароль для внешнего приложения, единственный адрес получателя и контрольный почтовый ящик. Значения секретов в спецификацию не включаются. |
| Внешние копии | Приватное S3-совместимое хранилище вне VPS, endpoint, bucket, ограниченная учётная запись, независимый ключ расшифровки. |
| Контент | Утверждённые категории, товары, цены, фото, контакты, доставка и текст страницы обработки данных. |
| Эксплуатация | Ответственный, контакт для оповещений, окна обслуживания и место хранения протоколов. |
| Карта доставки | При использовании живой карты — ключ нужного API и разрешение production-домена в кабинете поставщика. |

Пропущенные обязательные значения блокируют соответствующий этап и публичное открытие сайта. Имена поставщиков не выбираются автоматически. Выбор внешнего хранилища можно отложить до подготовки, но нельзя отложить до момента после открытия заявок.

### 3. VPS и доступ

- Базовая целевая ОС — Ubuntu Server 24.04 LTS amd64. Плановый начальный размер — 2 vCPU, 4 GiB RAM и 40 GiB SSD; это исходная конфигурация для проверки, а не обещание обслужить неизвестную нагрузку. Перед запуском измеряются свободное место, потребление контейнеров, объём media и временных архивов.
- Устанавливаются поддерживаемые Docker Engine и Compose v2 из официального репозитория. Версии фиксируются в записи о сервере. [Поддерживаемая установка Docker на Ubuntu](https://docs.docker.com/engine/install/ubuntu/).
- Создаётся отдельный оператор ОС. Контейнер приложения работает от непривилегированного пользователя; доступ к Docker socket выдаётся только оператору как административный доступ.
- Перед запретом паролей SSH и прямого root-входа проверяется вход новым ключом во второй сессии. Firewall включается после разрешения управляющего доступа. Аварийная консоль проверяется заранее.
- Настраиваются синхронизация часов, запуск Docker при загрузке, обновления безопасности ОС и управляемое окно перезагрузки. Образы приложения и PostgreSQL не обновляются автоматически между принятыми релизами.

### 4. Сети и firewall

- На хост публикуются только порты Nginx 80 и 443. PostgreSQL 5432, Gunicorn 8000 и служебные интерфейсы не публикуются ни на IPv4, ни на IPv6.
- Nginx и web соединяются через сеть прокси; web, worker и db — через сеть данных. Nginx не подключается к сети базы. Исходящая сеть worker сохраняет возможность DNS и TLS-соединения с `smtp.mail.ru:465`.
- Firewall провайдера, если доступен, и firewall хоста ограничивают SSH разрешёнными адресами. Наличие UFW не считается доказательством защиты опубликованных контейнерных портов: Docker может обходить его правила. При дополнительной фильтрации forwarding выбираются правила, совместимые с используемым Docker firewall backend. [Docker и UFW](https://docs.docker.com/engine/network/packet-filtering-firewalls/#docker-and-ufw).
- После запуска и перезагрузки проверяются итоговая публикация портов и доступность с внешней машины. Проверяется весь разрешённый перечень, включая управляющий SSH; не только отсутствие 5432.
- IPv6 по умолчанию не рекламируется через DNS. Если он включён, его маршрутизация, фильтрация, Nginx и внешние проверки выполняются наравне с IPv4.

### 5. DNS и владение доменом

- Регистрация проводится в учётной записи владельца с рабочим адресом восстановления, защитой входа и напоминанием о продлении. Учитывается цена продления; оплата домена и VPS обслуживается отдельно.
- DNS меняется у фактического авторитетного DNS-провайдера; он может отличаться от регистратора. Запись A основного имени указывает на IPv4 VPS. Проверяются авторитетные серверы и независимые рекурсивные резолверы.
- Для первого запуска TTL устанавливается 300 секунд. При смене существующего адреса TTL снижается заранее с учётом прежнего TTL. Ожидание выполняется по результатам DNS-запросов, без фиксированного обещания «всё обновится за несколько минут».
- AAAA создаётся только после успешной внешней IPv6-проверки. Устаревшая AAAA удаляется до выпуска сертификата. Проверяются также записи CAA, если они существуют, чтобы они допускали выбранный центр сертификации.
- На первом этапе используется прямое подключение к VPS без CDN-прокси. Это сохраняет существующую модель получения клиентского IP. Добавление CDN потребует отдельного изменения доверия к заголовкам и DNS-проверок.

### 6. Выпуск и продление сертификата

- Выбран метод: Let's Encrypt, Certbot на хосте, HTTP-01 через webroot, Nginx в Docker. Сертификаты и ACME-данные находятся в постоянном хранилище хоста вне релиза.
- Bootstrap-конфигурация Nginx обслуживает ACME challenge на публичном порту 80 и возвращает 503 для приложения. Она не ссылается на ещё не существующие TLS-файлы. Админка, формы и учётные данные через HTTP недоступны.
- После проверки DNS и challenge выполняется пробный выпуск через staging, затем выпуск рабочего сертификата. Staging-сертификат не используется для публичного сайта.
- Nginx получает read-only mount всего дерева сертификатов, включая цели ссылок на архив. Отдельный mount только файла текущего сертификата не используется. Ключи не помещаются в образ или Git; их права не расширяются ради удобства.
- После проверки конфигурации активируется TLS 1.2/1.3. HTTP перенаправляется на фиксированный основной HTTPS-hostname, кроме ACME challenge. Неизвестные Host/SNI отклоняются; перенаправление не строится из непроверенного клиентского Host.
- На хосте действует один scheduler продления не реже двух раз в сутки. После успешного продления deploy-hook проверяет конфигурацию Nginx и выполняет reload конкретного production-проекта. Ошибка hook считается эксплуатационной ошибкой, даже если Certbot сохранил сертификат.
- Приёмка проверяет `renew --dry-run` и hook с включённым запуском deploy-hooks. Сам по себе обычный dry-run не доказывает, что Nginx загрузит обновлённый сертификат. После hook снаружи проверяются HTTPS и обслуживаемый сертификат. [Certbot: webroot, renewal и deploy-hooks](https://eff-certbot.readthedocs.io/en/stable/using.html).

### 7. Django и доверие к прокси

- `DJANGO_DEBUG=false`; `DJANGO_ALLOWED_HOSTS` содержит только явно обслуживаемые имена, без wildcard. `DJANGO_CSRF_TRUSTED_ORIGINS` содержит их точные HTTPS-origins.
- Nginx перезаписывает `X-Real-IP` фактическим адресом прямого клиента и `X-Forwarded-Proto` фактической схемой. Клиентские значения этих заголовков не принимаются за доверенные. Прямое подключение к web из интернета отсутствует.
- После работы TLS включаются `DJANGO_TRUST_X_FORWARDED_PROTO`, `DJANGO_SECURE_SSL_REDIRECT`, `DJANGO_SESSION_COOKIE_SECURE` и `DJANGO_CSRF_COOKIE_SECURE`. Проверяются отсутствие циклических redirects, корректность CSRF и наличие Secure у cookies. [Django: HTTPS за доверенным прокси](https://docs.djangoproject.com/en/5.2/ref/settings/#secure-proxy-ssl-header).
- HSTS начинается с 300 секунд после успешной HTTPS-проверки. После семи дней стабильной работы и успешной проверки продления срок увеличивается до 31536000 секунд. `includeSubDomains` и `preload` остаются выключенными; это осознанное ограничение области политики, фиксируемое при разборе предупреждений Django. [Django: политика HTTPS](https://docs.djangoproject.com/en/5.2/topics/security/#ssl-https).
- Выполняются deployment checks с production-настройками и проверка отсутствия неприменённых миграций. Предупреждения разбираются поштучно; слабый ключ, DEBUG, неверные hosts, cookies или proxy-настройки блокируют запуск. Допустимые HSTS-предупреждения имеют записанное обоснование.

### 8. Секреты и роли PostgreSQL

- Production-секреты создаются отдельно от локальной среды и передаются контейнерам при запуске. Защищённый файл окружения принадлежит оператору, имеет права 0600 и закрытый родительский каталог. Он исключён из Git и build context.
- Каждый процесс получает только необходимые ему параметры. Общий файл со всеми секретами не подключается целиком к web/worker: bootstrap-credentials, ключ расшифровки копий и доступ к хранилищу резервирования в них не передаются.
- Значения не выводятся в команды диагностики, логи или протокол. Полный вывод объединённой Compose-конфигурации с подставленными секретами не публикуется.
- Bootstrap-администратор PostgreSQL используется только для создания базы и ролей. Учётные данные администратора не передаются web или worker.
- Роль миграций владеет схемой и объектами приложения, имеет нужные права DDL, но не имеет SUPERUSER, CREATEDB или CREATEROLE. Runtime-роль web/worker имеет CONNECT, USAGE на схему, необходимый DML на таблицы и доступ к последовательностям; без прав создания объектов и смены ролей.
- Bootstrap-процедура устанавливает владельца базы и схемы явно, проверяет наследуемые права и права PUBLIC. Ни принадлежность runtime-роли группе владельца, ни общие grants не должны возвращать ей запрещённый DDL.
- Production-конфигурация получает отдельные параметры runtime-пользователя и роли миграций вместо текущего использования общих bootstrap-credentials. Миграционные credentials передаются только одноразовому процессу миграции. Для вновь создаваемых таблиц и последовательностей задаются default privileges и проверяются фактические права после миграций.
- Пароли bootstrap, миграций и runtime уникальны. Учётные данные резервирования имеют только необходимые права чтения всей базы; восстановление выполняется отдельной административной процедурой. Ротация паролей учитывает реальные роли в PostgreSQL: смена переменной инициализации сама по себе не меняет пароль существующего тома.
- Отдельно предусмотрено защищённое восстановление секретов при потере VPS. Ключ расшифровки и доступ к внешним копиям не существуют только на потерянном сервере. Секреты не смешиваются с обычным архивом контента.

### 9. Воспроизводимый релиз и постоянные данные

- Релиз собирается из утверждённого чистого commit. Незакоммиченные изменения сначала рассматриваются и включаются в релиз обычным процессом; оператор не выбирает их содержимое автоматически.
- Web, worker и команды миграций используют один и тот же собранный образ. Образ идентифицируется commit и digest; изменяемый тег `local` не является идентификатором production-релиза.
- Зависимости устанавливаются по lock-файлу. Базовый Python/uv-образ, PostgreSQL, Nginx и вспомогательные образы закрепляются проверенными digests для выбранной архитектуры. Доступность образов проверяется до остановки рабочего сайта.
- Build context формируется из чистого релизного checkout; в него не попадают локальные конфигурации инструментов, ключи, внешние архивы, тестовые окружения или media. Собранные CSS/JS входят в релиз; их подготовка и соответствие исходникам проверяются до сборки образа.
- Образ приложения и манифест релиза сохраняются вне VPS либо в приватном registry, либо как защищённый экспорт образа. В манифест входят commit, digests, версии, состояние миграций и параметры без секретов. Для возврата используется уже собранный образ, без повторной сборки из изменившихся зависимостей.
- Production-проект Compose имеет постоянное имя. База и media используют явно определённые постоянные тома, не зависящие от каталога релиза. Том PostgreSQL 18 монтируется в соответствии с текущим layout официального образа.
- Статика собирается в отдельный том конкретного релиза. Nginx подключает соответствующий том read-only; откат возвращает статику вместе с образом. На первом этапе для неименованных по содержимому static-ресурсов используется повторная валидация кеша, без прежнего длительного неизменяемого кеширования.
- Media не является частью образа и не заменяется при обновлении. Проверяются права записи непривилегированного пользователя web, чтение Nginx, лимит загрузки 10 MiB и сохранность фото после пересоздания web.
- Удаление томов не является шагом деплоя, очистки или отката. Копирование каталога работающей PostgreSQL вместо корректного дампа не используется.

### 10. Готовность, обслуживание и автозапуск

- Для внутренних проверок web используется существующая главная страница, которая обращается к БД, с корректным разрешённым Host и корректным HTTPS-признаком только на внутренней проверке. Проверка не считается успешной по одному факту открытия TCP-порта или ответу redirect.
- Web считается готовым после миграций, успешного HTTP-ответа приложения и загрузки статики. Nginx может стартовать отдельно в bootstrap-режиме; режим публикации не включается по одному `service_started`.
- Worker не стартует до миграций, проверки SMTP и разрешения на обработку фактической очереди. На первом запуске используется один worker. Отдельная гарантия готовности почты проверяется через полный сценарий, а не статус контейнера.
- Для SIGTERM worker выделяется 120 секунд на завершение. Поскольку абсолютного deadline отправки сейчас нет, это уменьшает вероятность повторов, но не гарантирует их отсутствие после принудительной остановки.
- Nginx имеет управляемый режим обслуживания: 503, понятная страница и `Retry-After`, без обращения к Django. При первом запуске оператор проверяет приложение по HTTPS с разрешённого адреса, остальные посетители получают обслуживание. ACME challenge остаётся доступным.
- После открытия сайта административные маршруты остаются доступны только через HTTPS с разрешённых адресов оператора и сотрудников либо через утверждённый VPN. Изменение этого списка не требует открытия PostgreSQL или Gunicorn наружу.
- Restart policy и запуск Docker при загрузке обеспечивают старт production-сервисов после перезагрузки. Проверяется фактическое восстановление web, db, Nginx, worker и расписаний хоста. Остановка worker на время работ фиксируется так, чтобы перезагрузка во время обслуживания не запустила его неожиданно.

### 11. Перенос каталога и текстов

- Первая production-база создаётся заново. Сначала выполняются миграции; затем при необходимости импортируется только Category, Product, ProductImage, ContentPage и ContentSection из утверждённого источника.
- Выборочный импорт не включает Order, OrderItem, Inquiry, NotificationOutbox, счётчики форм, sessions, auth-пользователей, группы, Django Admin log и системные таблицы. Это правило относится к первому переносу контента; аварийные копии рабочего сайта, напротив, содержат полноценные данные приложения.
- Записи фиксированных страниц, созданные миграцией, обновляются по техническому ключу. Категории и товары сопоставляются по уникальному slug; секции — по странице и ключу. Фото сопоставляются по товару и относительному имени файла. Повтор импорта того же пакета не создаёт дубликаты и не удаляет не включённые в пакет записи.
- Импорт имеет предварительный отчёт без записи, проверку версий схемы, зависимостей, уникальности и предметной валидации. Сохранение каталога и текстов выполняется транзакционно. Файлы сначала проверяются и копируются в постоянное media, затем фиксируются ссылки в БД; оставшиеся после неудачи файлы описываются в отчёте и не удаляются вслепую.
- Пакет включает количество записей по сущностям и перечень файлов с размерами и checksums. Пути вне media, абсолютные пути и выход через ссылки не допускаются. После импорта проверяются связи, отсутствующие фото, цены, опубликованные товары и фактическое отображение.
- Создаются новый production-администратор и отдельные сотрудники с минимальными рабочими правами. Контакты, доставка и страница обработки данных должны содержать утверждённые материалы. Текстовый placeholder не считается доказательством, что формы отключены.

### 12. SMTP и outbox

- Для публикации выбран Mail.ru-профиль: SSL/TLS, `smtp.mail.ru`, порт 465, SMTP-адаптер проекта, пароль для внешнего приложения и совпадающий адрес аутентификации/отправителя. Сертификат проверяется, insecure auth выключен.
- С VPS проверяются исходящее подключение и успешный `check_notification_smtp`. Проверка выполняется с тем же окружением, что worker, не отправляет письмо и не обращается к очереди. Она не подтверждает доставку во входящие и не подходит для другого SMTP-host.
- До первого запуска worker проверяется, что новая база не содержит чужих или тестовых задач. При повторном запуске рабочая очередь сохраняется: проверяются pending, processing, истёкшие leases и manual_review; очищать очередь ради деплоя нельзя.
- Контрольные заявки маркируются как тестовые и используют синтетические контакты. До приёмки письма направляются в контрольный ящик; переключение на рабочий адрес проводится с остановкой worker и повторным preflight, без накопленных тестовых задач для нового получателя.
- `sent` означает принятие SMTP-сервером. Для приёмки дополнительно проверяется реальное письмо с соответствующим номером заявки в контрольном ящике, включая проверку спама.
- Доставка имеет семантику с возможным повтором при неопределённом SMTP-результате. После восстановления снимка очередь может отражать состояние до уже состоявшейся отправки: оператор сверяет неоднозначные задачи с журналом и получателем до разрешения повторной обработки.
- Ошибка почты не удаляет заявку. Используются существующие повторы и action для manual_review. Перерыв из-за квоты может превышать текущую политику повторов; такие задачи разбираются оператором, без обещания бесконечных автоматических повторов.

### 13. Резервирование

- Для первого этапа применяется логическое резервирование одной базы PostgreSQL вместе с согласованным media. Предлагаемые эксплуатационные цели: RPO не более 24 часов и RTO не более 4 часов. Это цели, подлежащие измерению; до успешного восстановления они не считаются доказанными.
- Согласованная пара создаётся дважды в сутки, в 02:00 и 14:00 UTC, а также до миграций или массового импорта. Копия считается завершённой только после успешной выгрузки и проверки объекта во внешнем хранилище.
- Deploy, backup и import используют общую блокировку на VPS. На время создания пары блокируется административное изменение каталога/контента и загрузка/удаление фото; завершаются уже выполнявшиеся записи. Все служебные операции изменения этих данных также используют блокировку. Приём заявок может продолжаться, так как он не меняет media.
- Пока каталог и media неизменны, создаётся транзакционно согласованный custom-format дамп всей базы и архив media. Учёт файлов, checksums, время начала снимка, версия PostgreSQL и идентификатор релиза записываются в один manifest. После создания локальной пары блокировка контента снимается; медленная внешняя выгрузка не удерживает админку. Сам `pg_dump` даёт согласованность базы, но не согласованность с изменяемыми файлами. [PostgreSQL: SQL dump](https://www.postgresql.org/docs/18/backup-dump.html).
- Дамп создаётся клиентом той же major-версии PostgreSQL, что сервер, и восстанавливается через `pg_restore` с остановкой при ошибках. Роли и права восстанавливаются отдельно по инфраструктурной процедуре; `pg_dump` не сохраняет роли кластера. [PostgreSQL: pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html).
- Артефакт шифруется до отправки. Bucket приватный, передача по TLS, доступ ограничен оператором и учётной записью резервирования. Отдельная процедура контролирует удаление старых копий; при наличии поддерживается versioning/защита от удаления.
- Хранятся все успешные пары за последние 14 дней, одна еженедельная за 8 недель и одна ежемесячная за 6 месяцев. Копии, используемые для текущего релиза или разбора аварии, не удаляются. Неудачная выгрузка не приводит к удалению последней рабочей копии.
- Возраст последнего внешнего снимка более 14 часов или любая ошибка очередного backup создают оповещение. Отсутствие пригодной копии младше 24 часов означает нарушение целевого RPO и требует реакции оператора.
- База резервируется целиком, включая заявки и outbox; media — целиком. Статика пересоздаётся из сохранённого релиза. Манифест конфигурации и возможность получить секреты также должны переживать потерю VPS.

### 14. Восстановление

- До открытия сайта копия скачивается из внешнего хранилища и расшифровывается в отдельной закрытой среде. Локальный исходный архив не подменяет эту проверку.
- Среда использует отдельные тома, базу, Compose-project, hosts и секреты. Production-DNS на неё не переключается. Worker выключен; исходящий SMTP блокируется дополнительно, чтобы случайный запуск процесса не отправил реальные уведомления.
- Восстановление происходит в пустую базу совместимой PostgreSQL, с известными ролями и версией приложения, указанной в manifest. До восстановления полного дампа не создаётся схема Django повторно миграциями. После восстановления проверяются состояние миграций, нужные права, media, счётчики последовательностей и загрузка страниц.
- Сверяются manifest и checksums файлов; проверяются реальные фотографии и связи записей, административный вход, каталог и формы. Для тестовых уведомлений используются только новые синтетические данные и изолированный почтовый получатель/локальный SMTP.
- RTO измеряется от начала процедуры аварийного восстановления до доступности принятого сайта, включая подготовку заменяющего VPS, получение секретов и образа, скачивание и расшифровку копии, восстановление и приёмку. Время от возникновения аварии до начала реакции оператора записывается отдельно; один замер скорости `pg_restore` не подтверждает RTO. Неуспешная проверка либо превышение RTO блокируют первый запуск до исправления процедуры или явного пересмотра цели владельцем.
- После публикации восстановление повторяется ежемесячно и после существенного изменения схемы, хранилища или способа копирования. Проверочная среда и её журналы имеют ограниченный доступ; реальные данные из копии не становятся публичными.
- При реальной аварии восстанавливаются полный рабочий дамп и media, затем проверяется неоднозначная очередь. Worker включается после этой сверки. Потеря данных после времени снимка фиксируется в протоколе и не скрывается успешным стартом контейнеров.

### 15. Наблюдение и журналы

- Внешняя проверка раз в минуту запрашивает основную HTTPS-страницу, проверяет ожидаемый контент и срок сертификата. Три последовательных сбоя создают оповещение. При обслуживании сигнал помечается плановым, но контроль сертификата и копий продолжает работать.
- Срок сертификата менее 21 дня создаёт предупреждение, менее 7 дней — срочное оповещение; ошибки scheduler и reload также наблюдаются.
- Раз в пять минут контролируются контейнеры, свободное место и возраст очереди. Менее 20% свободного диска — предупреждение, менее 10% — срочное оповещение. Незапланированно остановленный worker, любая manual_review и готовая к отправке задача, ожидающая более 10 минут, требуют разбора. Будущие запланированные повторы не ошибочно считаются немедленно просроченными.
- Nginx, Gunicorn, Django и worker пишут диагностические сообщения в обслуживаемые журналы. Для Docker применяется ротация с ограничением размера, исходно 10 MiB × 5 файлов на контейнер; оператор оценивает достаточность срока доступной истории при приёмке.
- Из access logs исключаются query strings и непредсказуемые токены подтверждения в URL. Не записываются тела POST, cookies, заголовки авторизации, контакты, письмо и credentials. В событиях worker сохраняются безопасные ID, результаты, длительности и коды ошибок.
- Healthchecks и статус контейнера служат сигналами наблюдения. Само состояние unhealthy без дополнительного механизма не обещает автоматический restart.
- Контакт оператора и канал оповещений задаются до открытия сайта. Отказ SMTP приложения не должен делать все инфраструктурные оповещения незаметными.

### 16. Исполняемый порядок первого запуска

| Этап | Действие | Условие перехода |
|---|---|---|
| 1 | Заполнить входные параметры, утвердить commit и материалы, подготовить production-конфигурацию и процедуры. | Релиз определён; доступы и внешнее хранилище доступны; секреты переданы защищённо. |
| 2 | Подготовить VPS, SSH, Docker, постоянные тома, firewall и аварийный доступ. | Новый SSH-вход и консоль проверены; свободного диска достаточно; порты заданы явно. |
| 3 | Собрать/получить и сохранить образы; создать production-базу и роли. | Все digests и архитектуры проверены; приложение не получает bootstrap-credentials. |
| 4 | Применить миграции от роли владельца, проверить runtime-права, собрать статику, импортировать контент и media, создать администратора. | Схема готова, импорт проверен, фото доступны; worker остановлен; приложение не открыто посетителям. |
| 5 | Настроить DNS; поднять HTTP-bootstrap Nginx; проверить challenge; выпустить и подключить сертификат. | DNS соответствует VPS; валидный сертификат обслуживается на 443; приложение через HTTP закрыто. |
| 6 | Включить production HTTPS-флаги; дать оператору закрытый доступ по HTTPS; выполнить deployment checks и проверить страницы/админку. | Нет циклических redirect и необоснованных предупреждений; cookies, CSRF, статика, media и клиентский IP корректны. |
| 7 | Настроить Mail.ru, проверить preflight и пустую/разрешённую очередь, запустить worker и выполнить контрольные заявки. | Заявки сохранены; соответствующие письма получены; фактическая очередь проверена. |
| 8 | Настроить расписания копий и сертификата, мониторинг; выгрузить согласованную копию и восстановить её отдельно. | Внешняя копия скачана и восстановлена; продление и hook проверены; оповещения работают. |
| 9 | Проверить перезагрузку VPS в закрытом режиме и повторить короткую HTTPS-проверку. | Сервисы и scheduler восстановились, данные и фото сохранены; внешняя проверка портов успешна. |
| 10 | Остановить worker для смены получателя, при необходимости установить рабочий адрес, выполнить preflight, проверить оставшиеся задачи и снова запустить worker; открыть посетителям приложение. | Релиз принят, контрольные задачи завершены, рабочие адреса верны, ответственный получил инструкции. |

Открытие маршрутов посетителям — последний отдельный шаг. До него публичный DNS и доступный challenge не означают, что сайт принимает рабочие заявки.

### 17. Обновление и откат

- До обслуживания новый образ уже собран, доступен и проверен в изолированной среде. Проанализированы миграции, изменение окружения и совместимость со старым релизом. Одновременный deploy исключён общей блокировкой.
- Включается обслуживание; новые записи блокируются, текущим запросам даётся завершиться. Worker останавливается с ожиданием завершения активной отправки. Создаётся и выгружается согласованная копия текущих БД/media; проверяется наличие предыдущего образа и соответствующей статики.
- Применяются миграции отдельной ролью, готовится статика нового релиза, пересоздаются необходимые web/worker/Nginx с новыми настройками. Смена окружения требует пересоздания контейнеров, одного restart недостаточно. После замены web проверяется, что Nginx направляет запросы в актуальный контейнер; при необходимости выполняется проверенный reload/пересоздание Nginx.
- В закрытом режиме проходят deployment checks и короткая приёмка. Перед worker выполняются preflight и сверка очереди. Только после успеха снимается обслуживание.
- Если миграции не выполнялись либо текущая схема совместима со старым кодом, возвращаются предыдущий образ, конфигурация и статика с сохранением рабочей базы.
- Если схема несовместима, автоматический возврат образа запрещён. Предпочтение отдаётся исправлению вперёд или заранее проверенной обратной миграции. Восстановление предрелизной копии допустимо только при установленном диапазоне потери записей, закрытых входящих запросах и зафиксированном решении ответственного.
- После открытия сайта новые заявки не уничтожаются молча восстановлением старого дампа. Перед таким восстановлением сохраняется текущая база для сверки и переноса принятых обращений. Незавершённые или неоднозначные отправки учитываются отдельно.
- Ошибка на любом этапе оставляет сайт в обслуживании и не считается успешным релизом. Действующая база, предыдущие образы и копии сохраняются; удаление томов не используется.

## Testing Decisions

### Граница и правила проверки

- Основная граница — существующий HTTPS-интерфейс сайта плюс наблюдаемые результаты в Django Admin и контрольном почтовом ящике. Создавать отдельный публичный test API не требуется.
- Проверяется внешнее поведение: сохранность заявки, корректность ответа, доступность ресурсов, получение письма и возможность восстановить рабочий сайт. Внутренние реализации Compose и worker не подменяют эти результаты.
- Граница приёмки вынесена пользователю на подтверждение согласно шагу 2 навыка `to-spec`. На момент подготовки документа ответ ещё не зафиксирован; публикация в трекер требует этого согласования.
- Проверки отказов, гонок и восстановления выполняются в изолированной среде. Production используется только для контролируемой краткой приёмки с синтетическими контактами, без запуска Django test runner на рабочей базе.
- При реализации сохраняются существующие тестовые границы Django Client и TransactionTestCase на отдельной PostgreSQL. Используются существующие проверки commit/rollback и конкурентных POST, workflow розницы/опта, SMTP preflight, уведомлений, клиентского IP, изоляции тестовой БД и карты доставки.
- Отключённый сценарий проверки на основной базе не используется. Исторические результаты тестов не считаются результатами будущего production-деплоя.

### Матрица приёмки

| ID | Проверка | Наблюдаемый результат |
|---|---|---|
| A01 | DNS с независимых резолверов и, если включён, IPv6 | Основное имя ведёт на нужный VPS; нет неработающей AAAA. |
| A02 | HTTP, HTTPS, сертификат и основной hostname | HTTP ведёт на основной HTTPS-домен; challenge доступен; сертификат доверенный, покрывает имена, цепочка корректна; неизвестный Host отклоняется. |
| A03 | Cookies, CSRF и подставленные proxy-заголовки | HTTPS работает без redirect loop; Secure выставлен; внешние поддельные заголовки не обходят определение IP и схемы. |
| A04 | Внешняя доступность портов по IPv4/IPv6 | Доступны только ожидаемые порты; SSH доступен лишь разрешённым адресам; PostgreSQL и Gunicorn недоступны. |
| A05 | Runtime-права PostgreSQL | Веб, админка и worker работают; runtime-роль не является superuser, не создаёт схему и не управляет ролями. |
| A06 | Страницы, статика, фото и загрузка изображения | Основные страницы отображаются; CSS/JS загружаются; фото видны; разрешённая загрузка работает и сохраняется после пересоздания web. |
| A07 | Импорт утверждённого пакета и его повтор | Количества и связи совпадают; нет дубликатов, пропущенных фото, тестовых заявок и импортированных auth-аккаунтов. |
| A08 | Розница: доставка и самовывоз | Получен номер; заявка и её снимок позиций есть в админке; доставка требует адрес; самовывоз доступен без адреса. |
| A09 | Оптовая форма | Отдельная заявка с номером есть в админке; ненужное описание потребности не требуется. |
| A10 | Повтор POST и основные формы без JavaScript | Нет дубликата заявки; штатные переходы и подтверждение работают без JS. |
| A11 | Уведомление через Mail.ru | Preflight успешен; письма по контрольным номерам получены; outbox показывает результат отправки без трактовки sent как доказательства inbox. |
| A12 | Остановленный worker и временная ошибка SMTP в изоляции | Заявка сохранена; очередь остаётся; после восстановления связи выполняется повтор; постоянный отказ имеет управляемый manual_review. |
| A13 | Внешняя копия | Завершённый зашифрованный комплект скачивается и расшифровывается независимо от исходного VPS; manifest и checksums совпадают. |
| A14 | Полное восстановление в новой закрытой среде | Каталог, заявки, фото, админка и схема восстановлены; реальные письма не отправлены; измеренное время соответствует RTO. |
| A15 | ACME-продление и deploy-hook | Staging-проверка продления и hook успешны; Nginx загружает действующий сертификат; HTTPS снаружи работает после reload. |
| A16 | Перезагрузка production-VPS до открытия | Данные не потеряны; необходимые контейнеры и расписания стартовали; сайт снова доступен оператору по HTTPS. |
| A17 | Обновление и совместимый откат в изоляции | Новый релиз проходит приёмку; предыдущий код и статика возвращаются по проверенной процедуре; база и media сохраняются. |
| A18 | Мониторинг и журналы | Проверочное событие доходит оператору; наблюдаются копии, диск, HTTPS и очередь; секретов, контактов и токенов в журналах нет. |
| A19 | Карта доставки | На production-домене карта отображается при рабочем ключе; при его отсутствии/отказе сохраняется предусмотренный fallback. |
| A20 | Контент и административные доступы | Реальные контакты и материалы опубликованы; сотрудник входит своим аккаунтом; лишних пользователей и прав нет. |

В протоколе записываются ID проверки, время UTC, релиз, среда, результат и безопасное подтверждение. Ошибки A01–A18 и A20 блокируют открытие заявок. Для A19 достаточен штатный fallback, если владелец не включил живую карту в обязательный состав запуска. Обнаруженные секреты в журнале требуют устранения источника и ротации затронутых credentials.

Во время подготовки этой спецификации тесты и сетевые проверки будущего VPS не запускались. Выполнена инспекция локальной конфигурации, исходников и официальной документации; матрица описывает необходимую будущую приёмку.

## Out of Scope

- Выбор конкретного регистратора, VPS-провайдера, региона хранения данных, тарифов и оплата услуг за владельца.
- Регистрация домена, создание VPS и выполнение реального деплоя в рамках текущего запроса на спецификацию.
- Изменение предметной логики каталога, корзины, заявок и уведомлений; создание нового публичного API.
- Платёжные системы, внешний сервис заказов и обмен с ним, складской учёт и оптовые тарифы.
- Redis, CDN, Kubernetes, несколько application-VPS, высокая доступность и обещание непрерывной работы при потере единственного сервера.
- PITR/WAL-архивирование и восстановление к произвольной секунде. Если установленное RPO окажется недостаточным, это отдельное расширение резервирования.
- Универсальный SMTP preflight для другого провайдера, доставка «ровно один раз» и гарантированное попадание каждого письма во входящие.
- HSTS preload, охват всех поддоменов HSTS и миграция PostgreSQL между major-версиями.
- Авторство юридических документов и определение правовых требований. В процесс поступают утверждённые владельцем материалы и регион размещения.
- Автоматическое восстановление старой production-копии с потерей новых заявок и автоматическая повторная отправка всех задач восстановленной очереди.

## Further Notes

Основные исправления исходного плана: введён bootstrap HTTPS без публичных HTTP-форм; разделены DNS и фактический DNS-провайдер; учтён обход UFW опубликованными Docker-портами; HTTPS-флаги привязаны к готовности TLS; зафиксирован Mail.ru-профиль preflight; разделены роли PostgreSQL; закреплены образы и статика; описан выборочный повторяемый импорт; резервирование перенесено до открытия заявок; определены согласованность DB/media, цели восстановления, расписания и retention; восстановленная очередь защищена от неожиданных отправок; добавлены наблюдение, перезагрузка, обновление и откат с учётом миграций.

Начальные размеры VPS, окна резервирования, retention, RPO/RTO и пороги оповещений — предложенные значения этой спецификации, а не ранее утверждённые владельцем показатели нагрузки или обязательства поставщиков. Их можно изменить до реализации с сохранением измеримой приёмки.

Для реализации потребуются отдельные подготовительные работы: production-конфигурация Compose/Nginx, разделение DB-credentials, сохранение релизов, режим обслуживания, операции импорта, backup/restore, scheduler сертификатов и мониторинг. Наличие этих пунктов в документе не означает, что они уже реализованы.

Удалённый Git-репозиторий проекта — `FrankHeels/Ribeshka`. Он является кандидатом для GitHub Issues, однако настройка трекера навыка `to-spec` не предоставлена, а в проверенном списке меток нет `ready-for-agent`. Согласно навыку перед публикацией нужно выполнить `/setup-matt-pocock-skills`, чтобы задать трекер и vocabulary меток. После настройки и согласования границы приёмки документ публикуется одной спецификацией с меткой `ready-for-agent`; дополнительный triage не требуется.
