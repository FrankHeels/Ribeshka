# Публичный запуск FishSite

Статус: целевой контракт постоянной эксплуатации. Фактический тестовый VPS описан в
[протоколе запуска](deployment-2026-10-23.md) и [переносе домена](domain-migration-2026-10-25.md).
Корневой Compose рассчитан на частную VM и HTTP; production — `deploy/production/`.
Автоматические выпуски и условия включения описаны в [CI/CD](ci-cd.md).
Наличие требований ниже не означает завершённую приёмку постоянной эксплуатации.

## Решения и входные данные

- Целевая ОС — Ubuntu Server 24.04 LTS amd64. Владелец выбрал Timeweb Cloud-30 как стартовый ориентир: 1
  vCPU, 2 ГБ RAM, 30 ГБ NVMe. До заказа перепроверь характеристики, регион, доступ к аварийной консоли и
  условия провайдера. Тариф — исходная точка измерений, не SLA и не обещание выдержать неизвестную нагрузку.
  Cloud-40 добавляет CPU и диск, но не RAM.
- До подготовки сервера зафиксируй домен и фактического DNS-провайдера, основной hostname, IPv4/IPv6,
  SSH/VPN операторов, утверждённый Git commit и образы, почтовый ящик/получателя, импортируемый
  каталог/media, ответственных и контакты для оповещений.
- До публикации выбери приватное внешнее хранилище резервных копий, независимый ключ восстановления и
  ответственного за них. Согласуй цели RPO/RTO и сроки хранения; оставляй их placeholders до решения
  владельца и измеренной проверки.
- Провайдеры, тарифы, DNS, storage, фактические секреты и личные данные не выводятся из примеров. Секреты
  передаются только через закрытое серверное окружение/secret store.

## Закрытый VPS и сеть

- Установи поддерживаемые Docker Engine и Compose v2, синхронизацию времени и обновления безопасности ОС.
  Создай отдельного оператора; контейнеры приложения запускай без root. Доступ к Docker socket считай
  административным доступом.
- Публикуй на VPS только Nginx `80/tcp` и `443/tcp`, а также SSH для разрешённых адресов/VPN. PostgreSQL
  `5432`, Gunicorn и служебные интерфейсы не публикуй ни по IPv4, ни по IPv6. Проверь также firewall
  провайдера: Docker может обходить правила UFW для опубликованных портов.
- Сначала подключай приложение напрямую к VPS без CDN. Текущая логика клиентского IP и proxy trust
  рассчитана на контролируемый Nginx; CDN требует отдельной настройки доверенной цепочки заголовков и
  приёмки.
- Nginx не должен иметь сетевого доступа к PostgreSQL. Web и worker получают только необходимые сети и
  секреты. В исходящей сети worker оставь DNS и TLS к выбранному SMTP-провайдеру; API МойСклад включай
  только по отдельному [руководству](moysklad-operations.md).
- После открытия сайта административные маршруты доступны по HTTPS только с разрешённых
  адресов сотрудников/оператора или через утверждённый VPN.
- Bootstrap Nginx публикует только ACME challenge и отказ `503` для приложения. Не обслуживай формы, админку
  или учётные данные по HTTP до готовности HTTPS.

## TLS, адреса и доверие к proxy

- Целевой выпуск: Let's Encrypt + Certbot на хосте, HTTP-01 через webroot, Nginx в Docker. DNS A должен
  вести на VPS; AAAA добавляй только после работающей IPv6-фильтрации и внешней проверки. Проверь CAA, если
  записи заданы.
- Сертификаты и ACME state живут вне релизного каталога. Nginx монтирует read-only всё дерево сертификатов,
  включая архивные цели ссылок; отдельный mount только текущего файла не подходит. Пробный выпуск staging не
  используется публично.
- После проверки TLS 1.2/1.3 HTTP перенаправляется на фиксированный основной HTTPS-hostname, кроме ACME
  challenge. Неизвестные Host/SNI отклоняются; redirect не строится из клиентского `Host`. Nginx
  перезаписывает `X-Real-IP` и `X-Forwarded-Proto`; Django доверяет proxy-заголовку только от
  контролируемого reverse proxy, а не произвольному заголовку клиента.
- Включи HSTS только после внешней проверки HTTPS и cookie/CSRF. Начальное значение — 300 секунд;
  после семи дней стабильной работы и проверенного renew увеличь до 31536000 секунд.
  `includeSubDomains=false` и `preload=false` остаются выключенными в этом scope.
- На хосте работает один scheduler Certbot с проверками не реже двух раз в сутки. Deploy-hook после
  успешного продления выполняет `nginx -t`, затем reload конкретного production Nginx. Приёмка включает
  `certbot renew --dry-run --run-deploy-hooks` и внешнюю проверку реально обслуживаемого сертификата после
  hook; успешный выпуск без успешного reload не считается готовностью.

## Релиз, база и импорт

- Развёртывай утверждённый чистый commit. Закрепи digest образов Python, PostgreSQL и Nginx; храни
  предыдущий принятый образ и соответствующую статику. В build context не включай `.env`, ключи, media,
  backup и тестовое окружение.
- Используй постоянный Compose project и именованные постоянные тома БД/media, не зависящие от каталога
  релиза. `down -v` не является обновлением, очисткой или откатом. После смены env пересоздавай нужные
  контейнеры: `restart` не перечитывает environment. После замены web проверь актуальный upstream Nginx и
  при необходимости проверь конфигурацию и перезагрузи/пересоздай Nginx.
- Раздели PostgreSQL schema-owner/migration credentials и runtime credentials web/worker. Runtime-роли не
  superuser, не владеют схемой, не создают таблицы/роли. Настрой default privileges владельца схемы так,
  чтобы будущие таблицы/sequence/grants были доступны нужным runtime-ролям без расширения их полномочий.
  Миграции выполняй отдельным процессом владельца схемы. Проверь PUBLIC и наследуемые
  права, чтобы они не возвращали runtime-роли DDL. Данные bootstrap-администратора
  передаются только процедуре создания БД и ролей.
- Перед импортом подготовь проверенный пакет только с утверждёнными категориями, товарами, ценами, текстами
  и media. Dry-run проверяет версии схемы, зависимости, уникальность, предметные ограничения, размеры и
  checksums файлов. Повторный импорт должен быть проверяемым и не создавать дубликаты.
- Первый импорт не переносит заявки, снимки, outbox, сессии, auth-пользователей, группы, логи админки или
  служебные таблицы. После импорта проверь связи, цены, опубликованные товары и фактическое отображение
  каждой категории media.

## Секреты, журналы и наблюдение

- Храни отдельные production credentials вне Git и образа; файл окружения принадлежит оператору, режим
  `0600`, родительский каталог закрыт. Каждый процесс получает только нужные ему секреты. Не печатай
  итоговый `docker compose config` с раскрытыми значениями.
- Включи Django HTTPS/proxy, redirect, Secure cookies и CSRF только после работающего HTTPS. Проверь
  `manage.py check --deploy`, предупреждения, внешние redirects, CSRF, cookies и обработку proxy-заголовков.
- Убирай из журналов тела POST, cookies, authorization, контакты, тексты писем, credentials, query strings и
  непредсказуемые токены в URL. Включи ротацию ограниченного размера. Доступ к копиям и журналам ограничь;
  реальные данные из restore не делай публичными.
- Мониторь по независимому от SMTP каналу: внешний HTTPS/ожидаемый контент/сертификат, контейнеры, диск и
  возраст последней внешней копии, возраст готовых задач и `manual_review`, scheduler и ошибки reload.
  Сбой почтового канала не должен скрывать сигнал об аварии копий или сайта. Числовые пороги согласуй и
  укажи как `{{порог}}` до запуска.
- `check_notification_smtp` проверяет выбранный профиль Mail.ru/TLS/AUTH, но не отправляет письмо и не
  проверяет БД/outbox. Перед worker проверь получателя и всю готовую очередь БД; `sent` подтверждает
  только принятие письма SMTP-транспортом. Подробности — [уведомления](wiki/notifications.md) и
  [реальная проверка Mail.ru](mailru-smtp-practical-test.md).

## Backup и restore

Обязательный механизм и контроль восстановления описаны отдельно в [контракте
резервирования](backup-restore.md). Он должен быть реализован и испытан до открытия публичного приёма
заявок. Согласованная копия включает PostgreSQL и media, общий lock с deploy/import, manifest, checksum,
шифрование до отправки в приватное внешнее хранилище и ключ восстановления вне VPS.

## Последовательность запуска и блокирующая приёмка

Публикуй формы только после всех блокирующих пунктов. В протоколе сохраняй UTC-время, commit/release, среду,
результат и безопасное доказательство; не копируй туда секреты и контакты.

1. Сверь домен, hostname, доступ оператора, параметры VPS, утверждённый релиз, почту, каталог и media;
   неизвестные обязательные значения оставь блокером.

2. Подними закрытую сеть, production DB roles/credentials, постоянные тома и миграции. Импортируй
   утверждённый пакет. Не открывай приложение посетителям.

3. Проверь внешний DNS и IPv4/IPv6. Убедись, что снаружи доступны только согласованные порты; DB/Gunicorn
   закрыты.

4. Выпусти сертификат, проверь hook/reload, включи HTTPS-параметры, запусти `manage.py check --deploy`;
   снаружи проверь сертификат, hostname и HTTP→HTTPS.

5. Готовность web подтверждай успешным HTTP-ответом приложения после миграций и загрузкой
   статики, с корректными Host и HTTPS-признаком; открытый TCP-порт или redirect недостаточны.
   Проверь страницы, CSS/JS, media, административный доступ, CSRF, cookies, формы и повтор POST. Проведи
   локальную/изолированную приёмку без Django test runner на рабочей БД.

6. Проверь SMTP preflight, очередь и тестового получателя. Создай синтетические контрольные заявки, проверь
   сохранение в админке и фактическое получение писем; включи рабочий получатель отдельно от тестового.

7. Получи внешнюю зашифрованную пару backup, восстанови её в закрытой среде и проверь manifest, файлы, media
   и целостность данных. Проверь внешнее оповещение об ошибке backup.

8. Перезагрузи VPS до открытия, проверь сервисы, scheduler Certbot и восстановление мониторинга. Только
   после записи всех результатов ответственный отдельно разрешает открытие сайта.

Блокирует открытие: незащищённый/неподтверждённый HTTPS, неправильные hostnames, открытый DB/Gunicorn порт,
runtime-superuser, неверные импортированные связи/media, сбой формы/CSRF, неразобранная рабочая очередь, не
полученное контрольное письмо, backup без независимого восстановления или отказ независимого канала
мониторинга. Живую карту можно считать необязательной только при явном утверждённом fallback.

## Обновление и аварийное восстановление

- Исключи параллельные deploy/backup/import одной общей блокировкой. Перед обновлением проверь образ,
  migrations, env и совместимость с предыдущим релизом; включи обслуживание и дождись текущих записей и
  активной доставки. Сними согласованный backup до миграций.
- Выполни миграции отдельной ролью, собери/разверни новый образ и статику, пересоздай процессы с новым
  environment, проверь фактический Nginx upstream и приёмку в закрытом режиме. До снятия обслуживания
  проверь очередь и SMTP.
- Кодовый rollback разрешён только при совместимой схеме. Иначе исправляй вперёд или применяй заранее
  проверенную обратную миграцию. Восстановление старой копии может потерять новые заявки: сначала закрой
  запись, сохрани текущую БД/media и согласуй диапазон потери/переноса.
- Restore выполняй в новую закрытую среду по manifest и точной major-версии PostgreSQL/release. На время
  приёмки должны быть выключены worker SMTP и MoySklad и отдельно заблокированы исходящие соединения к SMTP
  и API МойСклад. Сверь возможные неоднозначные отправки прежде чем включать их снова.
- Не очищай очередь при деплое. Не запускай Django test runner на production. Удаление постоянных томов
  запрещено в процедурах обновления, отката и восстановления.

Локальная VM и Compose — [текущая конфигурация](deployment-compose.md); отдельный тестовый кластер —
[тестовое окружение](test-environment.md). Эта спецификация описывает требуемое состояние, а не выданный
production acceptance.
