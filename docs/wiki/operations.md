# Развёртывание, эксплуатация и будущие интеграции

Читать при подготовке VPS, хранилища, резервных копий, мониторинга, кеша
и внешнего адаптера. Это целевая эксплуатационная схема MVP;
локальная настройка окружения описана в [README](../../README.md).

## Развёртывание

- Развёртывание: Docker Compose, Gunicorn, Nginx на VPS с HTTPS. Предусмотреть постоянное хранилище фотографий, резервные копии БД и фотографий, журнал ошибок и контроль неотправленных уведомлений. Не предполагать провайдера, домен, бюджет или показатели нагрузки.

Команда `process_notifications` развёртывается отдельным сервисом Compose из
того же образа приложения. Для локального теста подготовлен Compose-набор;
инструкция запуска — в [руководстве Docker Compose](../deployment-compose.md).
Её соединения, захваты, повторы и контроль неотправленных задач описаны в
[уведомлениях](notifications.md). Текущий Nginx слушает HTTP; перед публикацией
на VPS нужно настроить TLS-сертификат и HTTPS-конфигурацию Nginx, firewall,
production-настройки Django и внешние резервные копии с проверенным
восстановлением. Пошаговый список — в [руководстве Docker Compose](../deployment-compose.md#чеклист-перед-публичным-запуском-на-vps).

Локально задайте SMTP-настройки в gitignored `.env`; каждый Django-процесс
загрузит его автоматически, а переменные
окружения имеют приоритет. `source .env` не нужен. Не добавляйте файл в Git.
Для развёртывания передавайте настройки во внешнем окружении процесса или secret
store. Проверяйте конфигурацию до подключения worker к очереди: backend проверяется
до первого захвата. При смене `NOTIFICATION_BACKEND` остановите прежние процессы
до запуска новых. Неотправленные старые задачи читаются через текущий backend.
`sent` — подтверждение принятия транспортом, а не доставка в почтовый ящик.
SMTP timeout 10 секунд относится к отдельной сетевой операции; неопределённый
ответ может привести к безопасному повтору с прежним номером заявки.

Для отправки используется Mail.ru через `smtp.mail.ru:465`/SSL-TLS. Учетные
данные задаются адресом ящика и паролем для внешнего приложения; SMTP-доступ
должен быть включён в настройках ящика.
Перед запуском worker выполните `check_notification_smtp`; команда проверяет
соединение и SMTP AUTH без отправки и доступа к очереди. Локально пароль может
храниться в `.env` либо задаваться окружением; при
развёртывании используйте внешнее окружение или secret store. Перед ротацией
остановите старые процессы и проверьте новую конфигурацию. Лимиты отправки
определяются текущими правилами Mail.ru; постоянные ошибки или исчерпание попыток
переводят задачу в `manual_review`. Повторяйте её из админки после устранения
причины. Перед проверкой очереди используйте отдельную
локальную БД с синтетическими заявками; `--once` обрабатывает все задачи,
готовые в указанной БД.

Сотрудник с правом изменения уведомлений может вернуть выделенные задачи
`manual_review` в очередь. Действие сбрасывает счётчик и код ошибки, фиксирует
операцию в журнале Django Admin и отправляет пустой `pg_notify` в транзакции.

## Граница внешнего адаптера

- В `integrations` оставить границу для будущего адаптера внешнего сервиса заказов, который читает уже сохранённую заявку и собственную очередь доставки. До получения контракта сервиса не писать его API и не запускать обмен.

## Кеширование

- Redis откладываем на последующий этап: подключать через стандартный механизм кеширования Django при подтверждённой замерами потребности. При добавлении кеша предусмотреть его сброс после изменения цены или публикации товара и отделить персональные данные корзины от общего кеша.
