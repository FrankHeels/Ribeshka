# Email-уведомления и Transactional Outbox

Читать при работе с очередью, SMTP, worker и административным повтором отправки.
Реализованы атомарное создание outbox и `pg_notify`, SMTP-адаптер, команда
`process_notifications` и повтор `manual_review` из админки. Код не добавляет
миграцию: текущие поля модели хранят состояния, счётчик, безопасный код ошибки,
следующую попытку и lease. На отдельной PostgreSQL и локальном SMTP прошли
22 сценария уведомлений, включая публичные формы, конкурентные worker,
reconnect и восстановление после остановки процесса. Подробности и границы
проверки — в [слое данных](../data-layer.md#проверка-04102026-доставка-уведомлений).

## Архитектура

- Очередь уведомлений: PostgreSQL Transactional Outbox + `LISTEN/NOTIFY`. Worker — собственная Django management command `process_notifications`; она работает отдельно от HTTP-запросов покупателей. Отдельный сервис Compose из того же образа — эксплуатационная настройка, пока не созданная.

Получателя уведомлений задают настройки сервера, а не данные браузера.
Заявку, позиции и outbox сохранять атомарно; `pg_notify` вызывать на том же
соединении внутри транзакции. Порядок сохранения и поведение commit/rollback —
в [сценарии заявки](order-flow.md#подтверждение-и-сохранение-розничной-заявки).

- `NotificationOutbox` хранит задачи и их состояние; `NOTIFY` служит сигналом проверить таблицу. Пропуск, повтор или объединение сигналов не должны приводить к потере задач. Payload оставлять пустым, данные заявки читать из БД. Celery для MVP не вводить; очередь работает без Redis.

- Контракт адаптера принимает неизменяемый DTO сохранённой заявки и стабильный ключ `kind:submission_key`; транспортные адаптеры не имеют ORM и не реализуют собственные повторы. `NOTIFICATION_BACKEND` задаёт import path адаптера; перед сменой backend остановите прежние worker-процессы. Накопленные задачи при следующем запуске будут обработаны новым выбранным адаптером.

- Реализованный SMTP-адаптер использует одну серверную настройку `NOTIFICATION_TO_EMAIL`, `NOTIFICATION_FROM_EMAIL`, Django `EmailMessage` и текстовые шаблоны. Тип/номер заявки формируют тему; введённые покупателем значения входят только в тело. Стабильный `Message-ID` строится из ключа доставки и домена отправителя. Успешна только отправка с результатом `send() == 1`; `DEBUG` не включает заглушку.

- Worker один раз проверяет конфигурацию backend до первого claim. Для SMTP проверяются единственный адрес получателя и отправителя, host/port, положительный socket timeout, комплект учётных данных и взаимоисключающие TLS/SSL; lease должен быть не короче десяти socket timeout. AUTH credentials требуют TLS или SSL. Исключение для тестового SMTP действует только при явном `SMTP_ALLOW_INSECURE_LOCAL_AUTH=true` и буквальном loopback IP в `SMTP_HOST` (`127.0.0.1` или `::1`); по умолчанию выключено и DNS/удаленные адреса не допускает. `SMTP_USE_TLS`, `SMTP_USE_SSL` и `SMTP_ALLOW_INSECURE_LOCAL_AUTH` принимают только `true`/`false` без учета регистра; неверное значение вызывает `ImproperlyConfigured` с именем настройки без вывода значения. Значения по умолчанию: 5 попыток, база повтора 30 секунд, предел задержки 3600 секунд, socket timeout 10 секунд, lease 300 секунд, резервная проверка 60 секунд.

## Gmail SMTP

Выбран профиль личного Gmail: `smtp.gmail.com:587` с STARTTLS (`SMTP_USE_TLS=true`, `SMTP_USE_SSL=false`). Допускается профиль `smtp.gmail.com:465` с SSL (`SMTP_USE_TLS=false`, `SMTP_USE_SSL=true`), но он пока не проверялся с реальным аккаунтом. Для проверки нужен полный адрес Gmail в `SMTP_USERNAME`, отдельный пароль приложения и такой же адрес в `NOTIFICATION_FROM_EMAIL`. Локально настройки задаются в gitignored `.env`: каждый Django-процесс загружает его автоматически, а уже заданные переменные окружения имеют приоритет; `source .env` не нужен. Не добавляйте файл в Git. При развёртывании используйте внешнее окружение процесса или secret store. Пароль приложения требует включённой [двухэтапной аутентификации](https://support.google.com/accounts/answer/185839?hl=ru) и может быть недоступен для Advanced Protection, настройки второго этапа только аппаратными ключами или ограниченной политикой Workspace. См. [пароли приложений](https://support.google.com/accounts/answer/185833?hl=ru).

`check_notification_smtp` применим только к выбранному `SMTPNotificationBackend` и Gmail-профилям выше. Команда переиспользует валидацию SMTP-адаптера, выполняет только Django SMTP `open()` и `close()`, поэтому подтверждает TLS/auth, не отправляя письмо, не читая ORM и не обращаясь к outbox/БД. Перед сменой настроек или пароля остановите прежние worker-процессы; после обновления окружения выполните preflight и запускайте worker только при успехе.

Личный Gmail обычно ограничен примерно 500 сообщениями в сутки; Google Workspace — ориентировочно 2000. После превышения лимита отправка может быть приостановлена на 1–24 часа. Текущая политика (5 попыток, начиная с 30 секунд с удвоением) не покрывает такой перерыв: задача попадёт в `manual_review`; повторяйте её вручную после устранения причины. SMTP 5xx также переводятся в `manual_review`. Официальные сведения: [лимиты Gmail](https://support.google.com/mail/answer/22839?hl=ru) и [настройка SMTP-клиента](https://knowledge.workspace.google.com/admin/gmail/send-email-from-a-printer-scanner-or-app?hl=ru).

## LISTEN, переподключение и готовые задачи

- Worker держит отдельное постоянное соединение Psycopg 3 с `autocommit=True` для `LISTEN notification_outbox`; операции с задачами выполняет через отдельное соединение Django ORM. При старте и каждом переподключении сначала зарегистрировать `LISTEN` (autocommit завершает транзакцию команды), затем проверить таблицу и только после этого ждать сигналов. При сбое listener или ORM соединения закрываются и переподключение повторяется с увеличивающейся задержкой до 60 секунд. `SIGTERM`/`SIGINT` останавливают новые claims, завершают текущую отправку и восстанавливают обработчики сигналов.

- После сигнала обрабатывать все готовые задачи, выбирая их последовательно до опустошения доступной очереди. Не предполагать соответствие «один сигнал — одна задача». Когда работы нет, ожидать уведомление с таймаутом до ближайшего `next_attempt_at`, истечения захвата задачи либо резервной проверки — что наступит раньше. Интервал резервной проверки настраиваемый, по умолчанию 60 секунд; проверка подхватывает пропущенные сигналы и задачи без новых уведомлений.

## Захват, отправка и повтор

- Для захвата задачи используется короткая транзакция с `select_for_update(skip_locked=True)`, проверкой готовности и переводом в обработку с ограниченным сроком захвата и токеном владельца. После commit отправляется письмо без удержания блокировки БД. Результат записывает только текущий владелец при совпадении статуса/токена и непросроченном lease; просроченный захват допускает повторную обработку. SMTP timeout ограничивает сетевую операцию, а не всё письмо; абсолютного deadline нет, поэтому после долгой отправки возможен повтор.

- Сохраняются статус, число попыток, безопасный код последней ошибки и `next_attempt_at`. После временной ошибки назначается экспоненциальный повтор с пределом; постоянные и неизвестные ошибки либо исчерпание лимита переводятся в `manual_review`. Исчерпавший лимит истёкший lease не отправляется повторно автоматически. Административное действие с правом изменения блокирует строку, проверяет `manual_review`, сбрасывает счётчик/код, возвращает `pending`, вызывает `pg_notify` и создаёт Django Admin LogEntry в транзакции. `sent` нельзя повторить этим действием; активный `processing` не меняется.

- Увеличивать число worker'ов при росте очереди. `NOTIFY` пробуждает всех слушателей, распределение задач обеспечивает захват строк в БД. Контролировать ошибки worker'а, возраст ожидающих задач и число неотправленных уведомлений.

## Содержимое и гарантия доставки

- Письмо о розничной заявке содержит номер, контакты, товары, вес, цену/кг, сохранённые предварительные суммы и их итог, способ получения, адрес для доставки и комментарий. Способ получения в DTO остаётся кодом модели и переводится в SMTP-шаблоне. Письмо об опте содержит номер и контакты; новая публичная форма не собирает описание потребности. Сохранившееся описание исторической заявки можно включить при наличии.

- Не обещать «ровно одно письмо»: при неопределённом ответе SMTP возможен повтор с тем же номером заявки. Сбой почты не должен удалять принятую заявку; перезапуск worker не должен терять очередь.

- `sent` означает принятие письма SMTP-транспортом, а не подтверждение доставки/попадания во входящие. Логи содержат ID задачи, backend, результат, длительность и код ошибки; контакты, содержимое письма, credentials и raw SMTP exception туда не попадают.
