# Email-уведомления и Transactional Outbox

Читать при работе с очередью, SMTP, worker и административным повтором отправки.
Реализованы модель и просмотр outbox; отправка, NOTIFY/LISTEN, worker и ручной
повтор пока не реализованы. Ниже — требования MVP.

## Архитектура

- Очередь уведомлений: PostgreSQL Transactional Outbox + `LISTEN/NOTIFY`. Worker — собственная Django management command `process_notifications`, отдельный сервис Docker Compose из того же образа приложения. Для прослушивания использовать Psycopg 3; в MVP один worker отправляет письма последовательно, отдельно от HTTP-запросов покупателей.

Получателя уведомлений задают настройки сервера, а не данные браузера.
Заявку, позиции и outbox сохранять атомарно; `pg_notify` вызывать на том же
соединении внутри транзакции. Порядок сохранения и поведение commit/rollback —
в [сценарии заявки](order-flow.md#подтверждение-и-сохранение-розничной-заявки).

- `NotificationOutbox` хранит задачи и их состояние; `NOTIFY` служит сигналом проверить таблицу. Пропуск, повтор или объединение сигналов не должны приводить к потере задач. Payload оставлять пустым, данные заявки читать из БД. Celery для MVP не вводить; очередь работает без Redis.

## LISTEN, переподключение и готовые задачи

- Worker держит отдельное постоянное соединение Psycopg 3 с `autocommit=True` для `LISTEN notification_outbox`; операции с задачами выполняет через отдельное соединение Django ORM. При старте и каждом переподключении сначала зарегистрировать `LISTEN` с завершением его транзакции, затем проверить таблицу и только после этого ждать сигналов. При обрыве связи повторять подключение с увеличивающейся ограниченной задержкой.

- После сигнала обрабатывать все готовые задачи, выбирая их последовательно до опустошения доступной очереди. Не предполагать соответствие «один сигнал — одна задача». Когда работы нет, ожидать уведомление с таймаутом до ближайшего `next_attempt_at`, истечения захвата задачи либо резервной проверки — что наступит раньше. Интервал резервной проверки настраиваемый, по умолчанию 60 секунд; проверка подхватывает пропущенные сигналы и задачи без новых уведомлений.

## Захват, отправка и повтор

- Для захвата задачи использовать короткую транзакцию с `select_for_update(skip_locked=True)`, проверкой готовности и переводом в обработку с ограниченным сроком захвата и токеном владельца. После commit отправлять письмо через SMTP без удержания блокировки БД. Результат записывает только текущий владелец задачи; просроченный захват допускает повторную обработку. Ограничить время SMTP-операции и выбрать срок захвата с запасом относительно этого ограничения.

- Сохранять статус, число попыток, последнюю ошибку и `next_attempt_at`. После временной ошибки назначать повтор с увеличивающейся ограниченной задержкой; постоянные ошибки или исчерпание настраиваемого лимита попыток переводить в состояние для ручного разбора. В админке показывать неотправленные задачи и действие повтора; ручной повтор возвращает задачу в готовое состояние и вызывает `pg_notify` в той же транзакции.

- Увеличивать число worker'ов при росте очереди. `NOTIFY` пробуждает всех слушателей, распределение задач обеспечивает захват строк в БД. Контролировать ошибки worker'а, возраст ожидающих задач и число неотправленных уведомлений.

## Содержимое и гарантия доставки

- Письмо о розничной заявке содержит номер, контакты, товары, вес, цену/кг, предварительные суммы, способ получения, адрес для доставки и комментарий. Письмо об опте содержит номер, контакты и описание потребности.

- Не обещать «ровно одно письмо»: при неопределённом ответе SMTP возможен повтор с тем же номером заявки. Сбой почты не должен удалять принятую заявку; перезапуск worker не должен терять очередь.
