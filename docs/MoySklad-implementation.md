# Реализация интеграции МойСклад

Здесь собраны точки входа текущей реализации, связанные проверки и условия её приёмки. Бизнес-контракт принадлежит [плану](MoySklad-plan.md); команды и порядок включения — [руководству эксплуатации](moysklad-operations.md).

## Реализация в исходном коде

| Сценарий | Реализация и граница |
|---|---|
| Локальное принятие заявки | `orders/services/retail.py`, `orders/services/integration_handlers.py`: сохраняют заявку и снимки; публичный POST не вызывает внешний API. |
| Решение владельца и экспорт | `integrations/moysklad/order_export.py`: создаёт связь и задачу только для явно выбранного экспорта; сохраняет `approved_at`/`approved_by`, снимок конфигурации, подготовленный payload и стабильный `syncId`; неопределённый ответ восстанавливается поиском по тому же ID. |
| Каталог и цены | `integrations/moysklad/catalog_sync.py`, `price_sync.py`, `catalog/pricing.py`: сопоставление по внешнему UUID, кандидаты-черновики, блокировка неподходящих карточек, применение цены общим сервисом. |
| Webhook и восстановление | `integrations/moysklad/webhooks.py`: проверяет секрет и `requestId`, сохраняет inbox и задачу до ответа, дедуплицирует одинаковую доставку; worker затем перечитывает связанные товары. |
| Фоновые задачи и ограничения API | `integrations/moysklad/worker.py`, `queue.py`, `throttling.py`: API-задачи выполняются отдельно от веб-запросов, с сохранёнными lease, повторами и общим ограничителем аккаунта. |
| Учётный статус и удаление | `status_sync.py` только читает статус заказа; `order_deletion.py` выполняет отдельное подтверждённое владельцем удаление. |
| Настройка и доступ | `config.py`, `controls.py`, `fishsite/backoffice/moysklad_views.py`: проверяют серверную конфигурацию, разделяют роли владельца и технического администратора и показывают локальное состояние обмена. |

## Инварианты фонового обмена

- HTTP выполняется вне ORM-транзакций, через фиксированный API и разрешённые
  типы ресурсов, с TLS, без redirects и с общим ограниченным сроком чтения ответа.
  Произвольный URL из webhook или ответа провайдера не становится адресом запроса.
- Ограничение API и HTTP lease общие для аккаунта. Перед записью результата
  проверяется действующий lease token; просроченный исполнитель теряет право записи.
- После получения HTTP-слота транспорт повторно проверяет захват текущей задачи;
  для экспорта и чтения статуса — также отсутствие решения об удалении заявки.
  Отменённая или просроченная задача не отправляет запрос, HTTP-слот освобождается.
  Контекст задачи ограничен её выполнением и не переносится на диагностику.
- Перед HTTP-чтением цены фиксируются редакции цены, связи и запроса. Короткая
  транзакция применения повторно проверяет их и внешний UUID. Устаревший ответ
  отбрасывается; автоматическая задача перечитывает данные. Блокировки товара
  и внешней записи берутся в том же порядке, что при сохранении заявки.
- Приёмник подтверждает webhook только после durable-сохранения inbox и задачи.
  Повтор `requestId` с тем же нормализованным телом идемпотентен; другое тело
  конфликтует. Продвижение inbox и постановка обновлений цен атомарны.
- Неопределённый экспорт восстанавливается по закреплённым `syncId`, payload
  и конфигурации. Смена аккаунта, пространства или внешних связей не превращает
  старую попытку в новый заказ. Процедура разбора —
  [эксплуатация](moysklad-operations.md#неопределённая-передача-и-согласие).

## Схема и миграции

Модели интеграции объявлены в `integrations/moysklad/models.py` и подключены через `integrations/models.py`. В текущем дереве присутствуют миграции:

- `0007_moysklad_order_export_approval` добавляет nullable-аудит решения владельца. Старые неподтверждённые задачи не получают автоматического разрешения на новый POST.
- `0008_moysklad_order_deletion` добавляет маркер внешнего удаления, тип задачи и дополнительные права удаления для уже существующей группы Owner.
- `0009_consolidate_api_state` переносит наиболее строгие паузы и активный HTTP lease в состояние аккаунта, затем удаляет дубли транспортных полей из `MoySkladSyncState`.

Наличие файлов миграций в checkout не показывает, какие миграции применены к конкретной БД. Перед обновлением проверяйте `showmigrations` и полный `migrate --plan`; порядок обновления процессов описан в [руководстве](moysklad-operations.md#обновление-кода-и-схемы).

## Проверки в репозитории

Текущие regression-сценарии сгруппированы в следующих файлах; перечень указывает, где искать доказательства поведения, а не результат запуска тестов:

- `tests/test_moysklad_manual_export.py` — отдельное решение владельца, POST/CSRF/права, старые неподтверждённые задачи и отсутствие экспорта опта;
- `tests/test_moysklad_exports.py` и `tests/test_moysklad_recovery.py` — замороженный payload, деньги и вес, повтор по `syncId`, восстановление после сбоя, очередь и гонки;
- `tests/test_moysklad_prices.py`, `tests/test_moysklad_acceptance.py` и `tests/test_moysklad_identity_logging.py` — сопоставление, отложенные UUID, цены, неполная выгрузка, webhook и сверка после восстановления;
- `tests/test_moysklad_worker.py`, `tests/test_moysklad_transport.py` и `tests/test_moysklad_safety.py` — границы HTTP-клиента, права управления webhook, lease, throttling и безопасные ошибки;
- `tests/test_moysklad_backoffice_roles.py` — роли и защита действий панели.

## Условия приёмки

До рабочего включения проверяющий должен подтвердить каждый пункт на конфигурации целевого аккаунта и отдельно от синтетических тестов:

1. API читает заданные UUID и права подходят выбранным потокам; постоянные `account_id`, `environment` и `namespace` совпадают с сохранёнными задачами.
2. Каждая опубликованная карточка имеет одну подтверждённую связь с поддерживаемым товаром и единицей килограмм; неподходящая карточка блокируется до отдельного решения владельца.
3. Webhook принимает и сохраняет событие до ответа, одинаковый `requestId` не создаёт вторую обработку; ручная/восстановительная сверка ограничена связанными товарами.
4. Публичная заявка остаётся локальной. После решения владельца появляется ровно один документ с её снимками, `syncId`, суммой и контактами; документ не проведён, без НДС и резерва.
5. После timeout тот же `syncId` позволяет установить результат без дубля; возобновление worker обрабатывает накопленную очередь и не меняет уже принятые снимки.
6. Чтение статуса не меняет заявку; остановка интеграции не мешает приёму заявок и писем; сценарии не читают остатки и не блокируют подачу заявки.

Результаты mock-тестов не подтверждают права реального аккаунта, доставку
webhook или состояние миграций целевой БД. Проверка окружения —
[техническая диагностика](moysklad-operations.md#процессы-и-диагностика).
