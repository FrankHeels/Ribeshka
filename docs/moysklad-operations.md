Код обмена реализован. Живая приёмка цены, заказа и статуса выполнена 15.10.2026
в отдельном контуре; затем по решению владельца запущена временная демонстрация
основной БД через ngrok. Доказательства — в [журнале реализации](MoySklad-implementation.md#живой-обмен-и-интерфейс).
Постоянный запуск выполняется по [плану](MoySklad-plan.md#10-последовательность-реализации-и-приёмка)
после настройки рабочего HTTPS и замены демонстрационного оформления.
Декомпозиция и результаты разработки — [журнал реализации](MoySklad-implementation.md).
Все четыре потока по умолчанию выключены. Наличие токена не включает обмен;
для текущей демонстрации владелец явно разрешил их в состоянии БД.

В локальной основной БД уже применены добавочные миграции и импортирован реестр
из 123 записей. Backup БД и media проверен восстановлением. Решение владельца
о замене ассортимента и текущая публикация — в [таблице ассортимента](MoySklad-catalog-review.md).
Исторические 13 заявок не выгружены. Начало регистрации новых экспортов
зафиксировано 15.10.2026 в 19:23:04 UTC.

Команды текущего временного контура из корня проекта, каждая в своём терминале:

```sh
ngrok http 8000 --inspect=false --log=false --traffic-policy-file /private/tmp/fishsite-ngrok-policy.yml
.venv/bin/python /private/tmp/fishsite_moysklad_demo_manage.py runserver 127.0.0.1:8000 --noreload --insecure
.venv/bin/python /private/tmp/fishsite_moysklad_demo_manage.py process_moysklad
.venv/bin/python /private/tmp/fishsite_moysklad_demo_manage.py process_notifications
```

При снятии отслеживания контрольных заказов 15.10.2026 сервер, ngrok и оба
worker не обнаружены среди запущенных процессов. Команды выше позволяют
владельцу запустить временный контур вручную. Временные профили
хранятся в `/private/tmp`; они не заменяют постоянное развёртывание. Если
ngrok выдаст другой адрес, после остановки обмена выполните
`.venv/bin/python /private/tmp/fishsite_moysklad_prepare_demo_receiver.py`,
перезапустите сервер/worker с новым origin и выполните
`.venv/bin/python /private/tmp/fishsite_moysklad_demo_manage.py configure_moysklad_webhook`.
Namespace и сохранённые `syncId` при этом не меняйте. После паузы отдельно
разрешите потоки техническим администратором; границу экспорта не переносите.

Перед выключением туннеля сначала остановите приём новых сигналов и потоки:

```sh
.venv/bin/python /private/tmp/fishsite_moysklad_demo_manage.py shell -c "exec(open('/private/tmp/fishsite_moysklad_stop_demo_exchange.py').read())"
```

Помощник проверяет сохранённый ID, точный URL и тип только своего вебхука,
отключает его и четыре потока. После его успеха процессы можно завершить
`Ctrl+C`; очереди и исходная граница экспорта сохраняются.

## Конфигурация и границы

Настройки `MOYSKLAD_*` перечислены в `.env.example`. Секреты хранятся на сервере
в окружении или gitignored `.env`; в панель владельца и браузер они не попадают.
Для обычного worker используется API-токен с нужными правами. Регистрация
вебхука выполняется отдельной командой: она предпочитает `MOYSKLAD_ADMIN_TOKEN`,
если он задан, иначе использует `MOYSKLAD_API_TOKEN`. Текущий токен владельца
подтверждён как административный, дополнительный ключ для живой проверки не
нужен. Обычный клиент worker запрещает запись вебхуков; специальный режим
включает только административная команда. Фактические права проверяет API.

Зафиксируйте UUID аккаунта, типа розничной цены, RUB, кг, организации, общего
контрагента и начального статуса. `MOYSKLAD_NAMESPACE` — один постоянный UUID
для целевого окружения; не генерируйте его заново при перезапуске или ротации
токена. Проверочный контур использует другое имя окружения и другой namespace.
Копия БД для обычных тестов не получает рабочие токены и секрет вебхука.

После первоначального поиска двух отложенных позиций по коду закрепите их UUID
в `MOYSKLAD_DEFERRED_PRODUCT_IDS` через запятую. Последующее изменение кода не
разрешает их публикацию; повторное использование кода другим UUID не запрещает
новый товар автоматически.

Для автоматических цен нужны публичный HTTPS URL и случайный hex-секрет
минимум 256 бит. Полный URL имеет вид
`https://HOST/integrations/moysklad/webhooks/prices/SECRET/`.
Не публикуйте настоящий URL в тикете, документации или терминальном логе.
Прокси ограничивает тело 1 МиБ и не пишет этот маршрут в access/error-логи;
фильтры приложения скрывают URL вебхука. Только этот POST освобождён от CSRF.

Перед миграциями сделайте проверяемую копию БД и media. В дереве проекта могут
находиться ранее подготовленные миграции кабинета: проверьте весь `migrate
--plan`, включая удаление прежней истории цен. Не применяйте его к рабочей БД
только ради проверки подключения.

## Проверка и включение

После миграций целевой БД сначала выполните чтение справочников и проверку:

```sh
.venv/bin/python manage.py check_moysklad --discover
.venv/bin/python manage.py check_moysklad
```

Обе команды выполняют только GET. `--discover` читает не более одной страницы
по 100 объектов каждого справочника; `*_page_full` предупреждает, что список
неполон. Выводятся идентификаторы и безопасные коды, без контактов. Проверка
не запускает очереди, не снимает паузу автоматически и не означает приёмку
вебхука. При ошибке доступа разрешена отдельная проверка техническим администратором; обычные
потоки до её успеха сохраняют общую паузу аккаунта.

1. Заполните актуальные реквизиты, провайдеров и сроки в юридических документах.
   В исходниках уже указан получатель МойСклад/ООО «Логнекс», но оставшиеся
   `{{...}}` означают, что тексты ещё не готовы к публичному запуску. Реквизиты
   провайдера сверены с [официальной офертой](https://www.moysklad.ru/upload/files/oferta.pdf).
2. Подготовьте HTTPS-приёмник. В отдельном проверочном контуре подтвердите
   реальную доставку вебхука и применение розничной цены выделенного товара.
3. Разрешите ручной каталог и поставьте проход. Владелец сопоставляет UUID
   существующих карточек, проверяет оформление и создаёт недостающие карточки
   из кандидатов. Новые карточки создаются черновиками. Не сопоставляйте
   автоматически по названию, коду или артикулу.
4. Все публичные товары должны иметь проверенную связь и кг. Отложенные
   позиции из плана остаются вне публикации. Снятие интеграционной блокировки
   выполняется явно после успешного чтения исправленного товара.
5. Зарегистрируйте собственный рабочий вебхук, выполните полную сверку цен и
   обработайте inbox. После контрольного результата разрешите цены/статусы.
6. Проверьте контрольный заказ с синтетическими контактами: одну внешнюю
   запись, исходные цену/вес, RUB, отсутствие НДС, `reserve=0`, `applicable=false`.
   Перед передачей реальных заявок технический администратор явно начинает
   экспорт после согласования с владельцем.

```sh
.venv/bin/python manage.py set_moysklad_streams --username TECH_ADMIN --catalog on
.venv/bin/python manage.py sync_moysklad_catalog --username OWNER
.venv/bin/python manage.py configure_moysklad_webhook
.venv/bin/python manage.py reconcile_moysklad_prices --username OWNER
.venv/bin/python manage.py set_moysklad_streams --username TECH_ADMIN --prices on --statuses on
.venv/bin/python manage.py start_moysklad_export --username TECH_ADMIN
```

`OWNER` — обычная учётная запись владельца, `TECH_ADMIN` — активный staff
с `is_superuser`. Команды каталога/цен только ставят работу в очередь.
Владелец выполняет эти два действия на `/admin/moysklad/` после OTP.
Проверка подключения, переключение потоков и одобрение передачи доступны
только техническому администратору на `/admin/moysklad/technical/` и через
соответствующие команды. Прежнее разрешение `manage_moysklad` само по себе
не даёт технический доступ. GET обоих экранов читает только локальные данные
и исходный файл согласия, не вызывает API и не создаёт архивную редакцию.
`start_moysklad_export` сохраняет исходный `export_started_at` и текущую
архивную редакцию согласия. Заявки до этой границы остаются локальными.
Повтор действия закрепляет новую редакцию для будущих заявок; прежние
неодобренные экспорты самовольно не разрешаются. Открытая до обновления
документов форма сохраняет прежнее согласие и локальную заявку, но новая
передача с ним требует разбора (`consent_revision_not_approved`).

## Процессы и диагностика

На техническом экране показатели означают:

| Строка | Как читать |
|---|---|
| Последний heartbeat | Последний сигнал фоновой службы. При активном обмене задержка больше двух минут требует проверки процесса |
| Доступ API | Результат последней проверки ключа и прав. Прежний успех не гарантирует доступ сейчас |
| Пауза API до | До этого времени запросы отложены; пустое значение означает отсутствие назначенной паузы |
| Пауза передачи аккаунта | Остановлена отправка заявок, например из-за лимита документов; чтение других данных может продолжаться |
| UUID вебхука | Идентификатор регистрации уведомлений, не секретный адрес приёмника |
| Приём / обработка вебхука | Когда последний сигнал принят и когда обработан. Разница может означать ожидание в очереди |
| Последняя успешная полная сверка цен | Завершённая проверка всех связанных товаров, а не последнее отдельное изменение цены |
| Следующая сверка цен | Запланированное время запуска; для выполнения нужна работающая фоновая служба |
| Начало регистрации заявок | Нижняя граница для новых экспортных задач; исторические заявки автоматически не передаются |
| Одобренная редакция / дата регистрации | Какой архивный текст согласия разрешён и когда он сохранён; это отдельная дата от начала экспорта |

Четыре потока независимы: «Каталог» разрешает ручное получение сведений для
сопоставления без публикации карточек; «Автоматические цены» обновляет цены
связанных карточек; «Передача заявок» отправляет новые разрешённые заявки;
«Учётные статусы» получает состояние уже связанных заказов. Ни один поток
не ведёт остатки и не подтверждает покупателю наличие. Переключатель разрешает
работу, но не запускает серверную службу.

```sh
.venv/bin/python manage.py process_moysklad
.venv/bin/python manage.py process_notifications
```

Это независимые процессы и очереди PostgreSQL. Compose-сервис
`moysklad-worker` включается профилем `moysklad`:

```sh
docker compose --profile moysklad up -d
```

API-worker восстанавливает истёкшие захваты, слушает сигнал и проверяет очередь
не реже чем раз в 30 секунд. Общий HTTP lease и интервал не менее 0,5 секунды
разделяются всеми процессами и окружениями одного аккаунта. HTTP выполняется
вне транзакции с абсолютным deadline 60 секунд. `--once` выполняет один
цикл планирования и не более одной готовой задачи; это не полная выгрузка.

Каталог запускается вручную. Цены сверяются только по связанным UUID раз в
сутки, после включения и восстановления; незавершённый проход продолжается.
Действующие статусы проверяются раз в пять минут, терминальные — раз в сутки.
Случайное отсутствие вебхуков без изменений само по себе не является ошибкой.

Панель показывает времена и возраст heartbeat/цен/статусов, ожидающие задачи,
inbox, результаты проходов, кандидатов, блокировки и открытые инциденты.
Суммы, вес и исходные контакты заявки остаются только для чтения. Для повторов,
исправления экспортной привязки и связи с существующим документом требуется
причина; действия фиксируют автора. После неопределённого POST сначала
устанавливается результат по `syncId`. Уже связанный документ повторно не
создаётся и не перезаписывается исходной заявкой.

Если передача уже начиналась, а внешний UUID неизвестен, откройте розничную
заявку и выберите «Проверить результат передачи». После OTP укажите непустую
причину и подтверждение. Действие с CSRF ставит прежнюю задачу с тем же
`syncId`; worker только ищет документ, включая удалённые, и не выполняет POST.
Найденный UUID сохраняется даже при расхождении или удалении; результат требует
разбора без создания дубля. Полный валидный пустой ответ оставляет
`manual_review` / `export_absent` и журнал `resolve_export_absent`, разрешая
отдельное исправление идентичности или повтор владельцем. До него исправление
заблокировано. При разрешённом исправлении пересобирается payload, но исходные
позиции, цены, вес, контакты и согласие не редактируются. Потеря lease не даёт
применить результат поиска. Проверка ещё не начатой или уже связанной передачи
этим действием отклоняется.

SMTP-worker раз в минуту проверяет локальное здоровье интеграции, даже если
API-worker остановлен. Один открытый инцидент объединяет одну причину и
затронутые объекты; новый сбой после восстановления создаёт новый инцидент
и одну новую почтовую задачу. SMTP сохраняет прежнюю гарантию at-least-once.
Логи содержат безопасные коды и ID, без контактов, payload, токенов и raw API
ошибок. После временной ошибки API повторы продолжаются с задержками
30/120/600/1800 секунд, затем с небольшим случайным разбросом около 1800 секунд.
Неуспешный ручной каталог завершается и ждёт нового действия владельца.

Ошибка конфигурации мониторинга МойСклад, включая невалидный URL приёмника,
не останавливает SMTP розницы и опта. В журнале появляется
`integration_monitor_failure` / `monitor_unavailable`; проверка повторяется
не чаще раза в 60 секунд. Ошибки БД не подавляются этим обработчиком.
Исправьте конфигурацию и проверьте диагностику; обычные письма продолжают
обрабатываться независимо.

По [официальной тарифной таблице](https://www.moysklad.ru/subscription/),
проверенной 15.10.2026, на подтверждённом владельцем «Базовом» количество
документов не ограничено; предел 100 документов относится к бесплатному тарифу.
Опубликованного кода Remap для исчерпания количества документов не найдено.
`1070` ограничивает доступ к ресурсу тарифом, `1049`/`1073` относятся к запросам.
Семантическая пауза `document_limit` предусмотрена и проверяется mock API;
при смене тарифа/индивидуальных условий потребуется подтверждённый структурный
ответ провайдера. Произвольный текст ошибки не является основанием такой классификации.

## Остановка, очистка и восстановление

```sh
.venv/bin/python manage.py set_moysklad_streams --username TECH_ADMIN --prices off --export off --statuses off
.venv/bin/python manage.py cleanup_moysklad_inbox
```

Остановка отправки сохраняет регистрацию новых экспортных задач после границы
запуска. Приёмник продолжает сохранять inbox при отключённых ценах. Очистка
удаляет только обработанный inbox старше 30 дней; незавершённые события остаются.

До удаления приёмника отключите собственную регистрацию вебхука в МойСклад;
чужие вебхуки не меняйте. После восстановления приёмника поставьте сверку цен.
При ротации секрета согласованно обновите приёмник и свою регистрацию; команда
не должна захватывать чужую регистрацию по похожему URL.

Восстановление БД выполняйте с выключенными SMTP/API. Сначала сверяйте
сохранённые `syncId`, созданные внешние документы и интервал потери локальных
данных, затем возобновляйте экспорт. Независимо от старых дат успеха поставьте
восстановительную сверку цен. Внешние документы откат сайта не удаляет.
Резервные копии и подготовленные payload содержат персональные данные;
распространите доступ, хранение и удаление также на них и документы провайдера.

Возврат версии без приёмника требует предварительного отключения собственного
вебхука. Возврат до кода регистрации экспортных задач требует отдельного плана,
иначе новые локальные заявки во время отката не попадут в очередь.
