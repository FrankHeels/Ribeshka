# Обмен с МойСклад: настройка и эксплуатация

Этот документ владеет рабочими процедурами и безопасными операциями. Бизнес-правила описаны в [контракте интеграции](MoySklad-plan.md); архитектура и условия приёмки — в [карте реализации](MoySklad-implementation.md).

## Настройка аккаунта

Заполните настройки сервера по ключам из корневого [`.env.example`](../.env.example). Не копируйте реальные токены, секрет webhook, полный секретный URL или персональные данные в документацию, тикеты и логи. Код проверяет UUID, обязательные поля для разрешённых потоков и форму HTTPS URL. Для цен требуется URL приёмника вида `https://HOST/integrations/moysklad/webhooks/prices/SECRET/`; секрет должен быть случайным hex-значением длиной не менее 64 символов. Ограничение тела webhook в приложении — 1 МиБ; задайте совместимый предел на прокси и исключите этот путь из логов.

Зафиксируйте один `account_id`, `environment` и постоянный `namespace`. Не меняйте namespace при перезапуске или ротации API-токена: он участвует в идентичности экспортов. Переключение на другой аккаунт требует отдельного плана очереди; сохранённые задачи не перенаправляются автоматически.

Для каталога и цен нужны API-пользователь, UUID выбранного прайса, валюты и единицы. Для экспорта дополнительно требуются UUID организации, общего контрагента и начального статуса. Команда настройки webhook использует `MOYSKLAD_ADMIN_TOKEN`, если он задан, иначе `MOYSKLAD_API_TOKEN`; обычный API-клиент не может менять регистрации webhook. Фактические права проверяйте в целевом аккаунте.

Флаги окружения служат начальными значениями; сохранённые состояния потоков в БД могут их переопределять. Перед любым изменением посмотрите фактическое состояние в `/admin/moysklad/technical/`. Этот экран доступен техническому администратору — активному сотруднику с правами управления и `is_superuser`.

## Проверка и поэтапное включение

После проверки БД и конфигурации выполните команды из корня проекта:

```sh
.venv/bin/python manage.py check_moysklad --discover
.venv/bin/python manage.py check_moysklad
```

Обе команды выполняют только GET. `--discover` читает ограниченную страницу справочников. Успешная проверка доступа не подтверждает право создавать заказ и не проверяет доставку webhook.

Включайте потоки по одному после их приёмки. `TECH_ADMIN` ниже — существующий технический администратор; для команд ручного каталога и цен укажите обычного Owner, чтобы записать автора действия.

```sh
.venv/bin/python manage.py set_moysklad_streams --username TECH_ADMIN --catalog on
.venv/bin/python manage.py sync_moysklad_catalog --username OWNER
.venv/bin/python manage.py configure_moysklad_webhook
.venv/bin/python manage.py set_moysklad_streams --username TECH_ADMIN --prices on --statuses on
.venv/bin/python manage.py reconcile_moysklad_prices --username OWNER
.venv/bin/python manage.py start_moysklad_export --username TECH_ADMIN
```

Команды `sync_moysklad_catalog` и `reconcile_moysklad_prices` ставят проходы в очередь; сетевую работу выполняет запущенный worker. Owner проверяет кандидатов и связи в панели после OTP. Владелец публикует только проверенные карточки.

`start_moysklad_export` включает передачу, фиксирует исходную границу регистрации
и допустимую архивную редакцию согласия. Новые розничные заявки после этой
границы автоматически получают связь и API-задачу; исторические заявки не
подхватываются. Команда сама не выполняет HTTP-экспорт. При изменении текста
согласия технический администратор явно закрепляет новую редакцию для будущих заявок.

Регистрация webhook — отдельная внешняя запись. `configure_moysklad_webhook` настраивает только регистрацию этого окружения с точным URL; не редактируйте чужие webhook вручную. После смены URL/секрета синхронно обновите конфигурацию и собственную регистрацию, затем выполните сверку цен.

## Процессы и диагностика

API-очередь и SMTP-outbox обслуживаются разными процессами. Запуск из корня проекта:

```sh
.venv/bin/python manage.py process_moysklad
.venv/bin/python manage.py process_notifications
```

Для Compose у проекта есть профиль `moysklad`: `docker compose --profile moysklad up -d`. Успех одного процесса не означает успех другого. `process_moysklad --once` обрабатывает не более одной готовой задачи за один цикл и не заменяет постоянный worker.

Панель `/admin/moysklad/` предназначена владельцу для кандидатов, цен и состояния потоков. Техническая панель показывает heartbeat, доступ, активные переключатели, очереди, inbox, результаты проходов, блокировки и открытые инциденты. Панель читает локальное состояние; она не выполняет внешний запрос при каждом открытии. Отсутствие heartbeat дольше двух минут требует проверки worker и БД. Если задача экспорта имеет неопределённый исход, сначала используйте «Проверить результат передачи» в карточке заявки; не создавайте внешний документ вручную, пока прежний `syncId` не разрешён.

Временные сетевые ошибки сохраняют автоматическую задачу для повтора. Ошибки доступа и лимита API видны в технической диагностике. Ручной проход каталога завершается при ошибке, включая timeout, 5xx, 429 и потерю lease: после устранения причины владелец запускает его заново. Автоматические задачи цен восстанавливаются и повторяются самостоятельно. Персональные данные находятся в заявках и подготовленном payload; доступ к резервным копиям и внешним документам ограничьте по тем же правилам, что доступ к БД.

Для настройки и проверки SMTP см. [руководство уведомлений](wiki/notifications.md). Приём письма SMTP означает принятие транспортом, а не подтверждённую доставку во входящие.

## Неопределённая передача и согласие

«Проверить результат передачи» выполняет только поиск по прежнему `syncId`.
При полной однозначной пустой выдаче задача остаётся в `manual_review` с
`export_absent`; новая отправка требует отдельного решения. До разрешения
неопределённой попытки нельзя менять payload или экспортную идентичность.
Исправление привязки после подтверждённого отсутствия сохраняет исходные снимки
и фиксирует автора и причину. Уже известный документ повтором не переписывается.

`consent_revision_not_approved` означает, что архивная редакция заявки
не разрешена для передачи. Старая открытая форма может
сохранить локальную заявку и письмо со своей подписанной редакцией, но
экспорт останавливается до HTTP. Обычный retry и исправление связи не меняют
принятое согласие и не одобряют его редакцию. Повтор `start_moysklad_export`
закрепляет текущую редакцию для последующих заявок и сохраняет исходный момент
запуска; прежние одобренные снимки сохраняют разрешение.

## Остановка и восстановление

Чтобы приостановить поток, технический администратор выключает только нужные флаги, например:

```sh
.venv/bin/python manage.py set_moysklad_streams --username TECH_ADMIN --prices off --export off --statuses off
```

Задачи, связи и незавершённый inbox сохраняются; после начала экспорта новые
заявки продолжают регистрироваться и при паузе отправки. Пока приёмник доступен, webhook продолжает сохраняться и при выключенном применении цен. Публичная подача заявок и SMTP при этом остаются локально доступными. Для полной остановки дополнительно штатно остановите `process_moysklad`; перед удалением публичного приёмника отключите только собственную регистрацию webhook в МойСклад.

После восстановления приёмника/API включите нужный поток, проверьте очередь и запустите сверку цен. Перед возобновлением экспорта проверьте известные внешние UUID и нерешённые попытки по `syncId`. При восстановлении БД сверяйте локальные записи с внешними документами до продолжения экспорта: откат сайта не удаляет документы МойСклад.

Обработанный inbox и завершённые задачи при нём старше 30 дней можно очистить командой; незавершённые события сохраняются:

```sh
.venv/bin/python manage.py cleanup_moysklad_inbox
```

## Обновление кода и схемы

Проверьте `showmigrations` и полный `migrate --plan` целевой БД, подготовьте
проверяемую резервную копию и совместимый план отката. Наличие файла миграции
не подтверждает её применение.

Перед изменением схемы штатно остановите web, API-worker и SMTP-worker.
Примените миграции вместе с соответствующей версией кода, затем запустите
новые процессы и проверьте heartbeat и очереди. Возврат старого кода допустим
только при совместимости схемы, регистрации экспортных задач и собственного webhook.
