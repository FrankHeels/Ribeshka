# Сценарии проверки Gmail SMTP

Исторический отчёт о прежнем Gmail-профиле. Текущий рабочий профиль Mail.ru и
инструкции по его настройке описаны в [документе уведомлений](wiki/notifications.md)
и [практическом руководстве](mailru-smtp-practical-test.md).

Проверка относится к `check_notification_smtp` и существующей доставке
розничных и оптовых заявок через outbox. Автоматические тесты используют подставные настройки,
моки SMTP и настоящий SMTP-сервер только на loopback. Подключения к Google и
отправка реальных писем в эти тесты не входят.

## Проверка подключения без отправки

Тесты команды выполняются через `SimpleTestCase`, запрещающий запросы к БД.
Для проверки порядка TLS/AUTH использовать настоящий Django SMTP backend с
подменёнными сетевыми SMTP-клиентами. Проверка только вызова `open()` через
мок всей библиотеки недостаточна для сценариев G01, G02 и G05.

| ID | Действие | Ожидаемый результат |
|---|---|---|
| G01 | Корректный профиль `587/STARTTLS` | TLS выполняется до AUTH; SSL-контекст требует доверенного сертификата и проверки hostname; соединение закрыто. |
| G02 | Корректный профиль `465/SSL` | Используется SMTP_SSL с проверяемым SSL-контекстом; STARTTLS не вызывается; затем AUTH и закрытие. |
| G03 | Неверный backend, host, сочетание порта и TLS/SSL, пустые credentials, неправильный email, несовпадение From/login, включённое локальное исключение | Отказ до сетевого соединения; backend, выбранный вместо SMTP, не загружается; ошибка содержит только безопасный код. |
| G04 | Успех и ошибки команды с запретом запросов к БД и отправки писем | Нет system/migration checks, ORM, захвата очереди, вызовов отправки, MAIL, RCPT или DATA. |
| G05 | Ошибка сертификата или STARTTLS | Нет AUTH и отправки после ошибки TLS; нет перехода на незашифрованное соединение; ошибка безопасна, соединение закрывается. |
| G06 | SMTP 535, сетевой timeout, отказ при создании соединения, неожиданное исключение и неверные числовые SMTP/NOTIFICATION-переменные при запуске из терминала с секретным маркером | Команда завершается ошибкой; stdout, stderr, логи и traceback не содержат credentials, адресов и исходного ответа SMTP. Ошибка разбора числа показывает только имя настройки и ожидаемый тип. |
| G07 | Ошибка закрытия после успеха либо одновременно с ошибкой AUTH | Нет сообщения об успехе; ошибка закрытия не скрывает первоначальную ошибку; диагностические данные безопасны. |
| G08 | `open()` возвращает False или None | Нет сообщения об успехе; соединение закрывается; возвращается безопасный код ошибки. |
| G09 | Выполнить успешную и неуспешную проверку при существующих заявках и pending outbox | Все поля заявок, снимков позиций и outbox остаются прежними, включая счётчик попыток и lease. |

## Безопасность и целостность доставки

Для интеграционных тестов использовать одноразовую PostgreSQL
`test_fishsite_gmail_validation`, создаваемую Django test runner. Проверять имя
БД до сценариев; основную `fishsite` и runner для основной БД не использовать.
Существующие тесты повторно использовать там, где они уже проверяют нужное
поведение; новые тесты добавлять для недостающих доказательств.

| ID | Действие | Ожидаемый результат |
|---|---|---|
| Q01 | Сохранить обе публичные формы и обработать очередь локальным SMTP | Сохраняются заявки и outbox; два письма соответствуют сохранённым заявкам; задачи становятся sent. |
| Q02 | Передать попытку изменения адресата/отправителя через данные формы и строки вида Bcc/To в комментарии | SMTP envelope и заголовки используют только серверные адреса; покупательские данные остаются в теле; дополнительные адресаты не появляются. |
| Q03 | После сохранения изменить или удалить товар в каталоге | Письмо содержит сохранённые название, цену, вес и суммы; изменения каталога не меняют снимок заявки. |
| Q04 | Ошибка AUTH либо сертификата при отправке обеих заявок | Заявки и позиции полностью сохраняются; outbox становится manual_review с безопасным кодом; sent_at не заполняется; секреты не попадают в логи/БД. |
| Q05 | Временный SMTP-сбой, повтор, исчерпание лимита и административный повтор | Корректные переходы pending/manual_review, сроки и счётчик; повтор не создаёт новую заявку; права администратора проверяются. |
| Q06 | Конкурирующие worker, остановка процесса, потеря подтверждения или ошибка БД после приёма письма | Lease восстанавливается; устаревший worker не финализирует чужой захват; заявка не теряется; при повторе стабилен Message-ID. Дубликат письма допустим при неопределённом результате SMTP. |

## Команды и границы приёмки

```sh
.venv/bin/python scripts/test_postgres.py start
.venv/bin/python manage.py test tests.test_notification_smtp_preflight \
  tests.test_notifications tests.test_request_workflows \
  --settings=fishsite.settings_test --noinput
```

Используется отдельный PostgreSQL 18.6 на `127.0.0.1:15432`, роль
`fishsite_tester`, БД `test_fishsite`. Настройка и полный прогон описаны в
[тестовом окружении](test-environment.md). Старые команды с `DJANGO_DB_*`
для выбора тестовой БД больше не применяются.

Автотесты доказывают локальное поведение и выбранные настройки TLS. Реальную
авторизацию Gmail, сертификат удалённого сервера и получение писем владельцем
проверять отдельно по [README](../README.md#локальная-проверка-gmail), когда
аккаунт будет готов. `sent` подтверждает принятие SMTP, а не попадание во входящие.

## Результат локальной проверки 05.10.2026

- Отдельный модуль проверки подключения: 10 тестов, 0,362 секунды, успешно.
- Комбинированный прогон трёх модулей выше: 49 тестов, 20,854 секунды, успешно.
  Django создал и удалил `test_fishsite_gmail_validation`; последующий запрос
  к списку БД подтвердил отсутствие тестовой и базовой проверочной БД.
- После расширения G07 явным сочетанием SMTP AUTH 535 и ошибки закрытия
  повторно проверен только этот тест: 1 тест, 0,015 секунды, успешно.
- `manage.py check` и `git diff --check` прошли. Независимая проверка исходного
  кода существенных оставшихся замечаний не выявила.

Код сценариев находится в [проверках подключения](../tests/test_notification_smtp_preflight.py)
и [проверках уведомлений](../tests/test_notifications.py). Остальные сценарии
форм проверяются [тестами сохранения заявок](../tests/test_request_workflows.py).
Основную очередь `fishsite` не обрабатывали; к Gmail не подключались.

## Попытка реальной проверки 05.10.2026

SMTP-параметры из локального `.env` переданы в окружение отдельного проверочного
процесса без вывода значений. Файл исключён из Git. Настройки выбранного профиля
`smtp.gmail.com:587`/STARTTLS прошли проверку, однако соединение не дошло до AUTH.

- На порту 587 SMTP-приветствие не получено: timeout даже при ожидании 20 секунд.
- На порту 465 проверка альтернативного соединения завершилась timeout на TLS handshake.
- HTTPS `mail.google.com:443` доступен; соединение TLS 1.3 с проверкой сертификата успешно.
- Проверка повторена вне ограниченной среды выполнения с тем же результатом.
- Отправлено 0 писем; отдельная проверочная БД ещё не создавалась, основная
  очередь и сохранённые заявки не обрабатывались.

Пользователь сообщил, что VPN не используется. Для следующей проверки предложено
сменить сеть, чтобы проверить зависимость результата от текущего сетевого доступа.
После самостоятельного повторного запуска пользователь передал успешный результат
`preflight`: TLS и авторизация Gmail подтверждены, письма этим этапом не отправляются.
Одноразовый скрипт остановился с `KeyError`: он ожидал CSRF-cookie от пустой
корзины, где форма ещё не показана. Скрипт исправлен: токен получают со страницы
товара; при запуске worker также восстанавливается SMTP backend, который
`setup_test_environment` временно заменяет на locmem.

В созданной отдельной БД проверено отсутствие заявок и задач outbox. Исправленный
сценарий прошёл локальный прогон с двумя имитациями отправки, проверкой неизменности
сохранённых заявок и откатом изменений. Реальных писем в этом прогоне не отправляли.
Повторный запуск `deliver_once` разрешён только при нуле предыдущих попыток и
отсутствии заявок/outbox; созданные до ошибки синтетические каталог и товар
используются повторно.

## Успешная реальная доставка 05.10.2026

После повторного запуска `deliver_once` результат одноразового скрипта подтвердил:

- Розничная заявка `R-DBEC56FC65` и оптовый запрос `W-C4225D98CE` получили
  статус outbox `sent`, каждый с одной попытки, без кода ошибки и с `sent_at`.
- Сохранённые заявки и снимок розничной позиции не изменились при отправке
  (`saved_requests_unchanged: true`); контрольная сумма заказа — 376,50.
- Пользователь отдельно подтвердил фактическое получение тестовых писем.

Таким образом, проверены TLS/AUTH Gmail и реальная отправка обоих видов заявок
через существующие SMTP-адаптер и outbox worker в отдельной тестовой БД.
Проверка не подтверждает запуск постоянного worker в целевом окружении.

## Проверка автоматической загрузки .env 06.10.2026

`fishsite/settings.py` загружает корневой `.env` через `python-dotenv` до чтения
настроек, с `override=False`. Проверено в отдельных процессах: параметры БД и
SMTP читаются из файла без ручного экспорта; существующие переменные окружения
имеют приоритет. Значения секретов в вывод не попадали. Зависимость, `uv.lock`
и установленная версия `python-dotenv` 1.2.4 согласованы.

- `manage.py check` прошёл.
- `migrate --check` для основной БД прошёл без `source .env`, с предварительным
  удалением файловых параметров из окружения проверочного процесса; БД не менялась.
- 49 тестов подключения, доставки уведомлений и публичных заявок прошли за
  20,994 секунды в одноразовой PostgreSQL-БД; тестовая БД удалена Django.
  SMTP был фиктивным/локальным, основная очередь не обрабатывалась,
  реальных писем в этом прогоне не отправляли.

Ручной запуск на основной локальной БД описан в
[практическом гайде](gmail-smtp-practical-test.md).

## Проверка подмены POST через Chrome DevTools MCP 06.10.2026

Проверен текущий рабочий код в отдельном локальном экземпляре сайта:
временный кластер PostgreSQL с БД `fishsite_post_check`, отдельный браузерный
контекст Chrome, синтетические товар и контакты. Основная БД и `.env` не
использовались. Worker не запускался; отправлено 0 писем.

Через браузер добавлены 3 кг тестового товара с ценой 250,75 ₽/кг.
Исходный POST формы записан Chrome DevTools MCP; изменённые копии отправлены
через `fetch` в той же браузерной сессии, с исходным CSRF-токеном.

| Проверка | Фактический результат |
|---|---|
| Имя из трёх пробелов, остальные поля корректны | POST 400, ошибка обязательного имени; 0 заявок, позиций и outbox. |
| В записанном POST имя заменено на корректное, к `submission_token` добавлен `x` | POST 400, сообщение «Форма устарела»; 0 заявок, позиций и outbox. |
| Исходный корректный токен и имя, добавлены `price_per_kg=1&total=1` | POST 302, страница успеха 200; сохранены цена 250,75 ₽/кг, вес 3 кг и сумма 752,25 ₽. |

После последнего запроса прямым чтением временной БД подтверждены ровно
1 заявка, 1 позиция и 1 связанный outbox в `pending` с `attempt_count=0`.
Дополнительно проверено тело записанных сетевых запросов: изменённый токен
действительно отправлен, а успешный запрос содержит подставные цену и итог
при сохранении исходного токена. Ответы имеют `private, no-store`.

Это проверка защиты от подмены конкретных полей, а не полный аудит безопасности
или проверка доставки Gmail. После проверки временные процессы остановлены,
браузерная вкладка закрыта, временный кластер и копия проекта удалены.
